# juja-builder

- (이름) 조선의 활자 주조 관청 주자소(鑄字所)에서 주자(鑄字)를 juja로, 소(所)를 builder로 옮긴 이름
- (목적) 심사위원이 세부평가항목별 답을 원고에서 바로 찾을 수 있는 제안서 작성
- (목표) 코드 점검과 렌더링 검수를 통과한 hwpx와 docx 납품본 산출
- (범위) 연구, 기획, 운영 용역 입찰에 내는 정성제안서
    + (대상 과업) 전략기획과 기본계획 수립, 정보화계획(의무 ISP, 지능정보사회계획, 발주처 자체 IT 기획), 사업기획(R&D, 비R&D), 성과분석과 평가 대응(R&D, 비R&D), 정책연구와 조사분석(실태조사, 동향조사, 수요조사, 제도 개선, 과제 발굴), 경영평가 대응, 지원사업 운영. 유형별 판별 신호는 과업 유형별 모듈 골격 절
    + (제외 대상) 시스템 구축 사업(SI), 국가연구개발과제 연구개발계획서, 공모사업 사업계획서
    + (정보화 과업의 경계) 결과물이 계획서인 정보화 기획(ISP 등)은 대상. 결과물이 시스템인 구축 사업은 제외. 판정 기준은 결과물의 형태. 법령상 소프트웨어사업 해당 여부는 판정 기준 밖
    + (제외 대상 입력) RFP가 제외 대상이면 착수 질의 전에 유저에게 범위 밖임을 알림
    + (부가 산출) 사전진단보고서와 기획보고서. 판별과 절차는 산출 유형 절
- 기본 입력은 RFP 1건. 제안 발표자료(pptx, pdf)가 입력에 있으면 발표자료 변환 경로(절차 절)를 적용
- 제안서의 산출 파일은 제안전략서, 요구항목표, 배점표, 섹션대장, 모듈총괄표, 스토리라인, 섹션별 원고, 점검기록, hwpx 또는 docx 납품본
- 이 스킬이 만드는 파일은 전부 작업폴더에 생성. 대화 응답의 기재 범위는 대화 응답 절
- 스크립트는 `<SKILL>/scripts/proposal.py`. 호출 형식은 `python3 <SKILL>/scripts/proposal.py 명령 인자`. `<SKILL>`은 SKILL.md가 있는 폴더
- 조판 코드는 같은 폴더의 `hwpx_report.py`(원고 파서와 표 배치 산정 같은 형식 무관 조판 계층, hwpx 작성기)와 `docx_report.py`(docx 작성기). 두 파일의 조판 규범은 수정하지 않음(허용 범위는 준비 절의 API 호출부 수정)
- 참조 파일은 `<SKILL>/references` 폴더에 수록. 읽는 시점과 범위는 아래 표

| 파일 | 수록 내용 | 읽는 시점과 범위 |
|------|-----------|------------------|
| methods.md | 과업 유형별 모듈 골격, 모듈과 Task의 목적, Task 유형별 라벨 세트, 회의체 설계, 의견수렴 도구 | 2단계에 서두, 공통 표준, 해당 과업 유형 절(복합 과업은 해당 유형 전부). 판별 신호에 걸리지 않는 과업은 0단계에 서두를 먼저 읽음 |

| report.md | 사전진단보고서의 절차, 진단 설계, RFP 우선 원칙, 목차 도출과 목차 사례, 스토리라인 확정, 자료 조사, 원고 작성, 점검 대상, 조판 옵션 | 산출 유형이 사전진단보고서일 때 `init` 직후 전체 |

## 산출 유형

| 유형 | 판별 신호 | init | 절차 원천 | 번호 체계 |
|------|-----------|------|-----------|-----------|
| 제안서 (기본) | 제안서, 정성제안서, 입찰, 제안요청서 | `init 작업폴더` | SKILL.md 절차 절 | Ⅰ. 1. 가. 1), 무번호 캡션 |
| 사전진단보고서 | 사전진단보고서, RFP로 보고서, 연구보고서 초안(전략기획, 사업기획, 타당성 조사, 성과분석, R&D 성과평가, 정보화계획, 수요조사, 동향 조사분석 등), 착수 전 진단 | `init 작업폴더 --kind report` | references/report.md | 제1장 1.1 1.1.1 가., 장별 번호 캡션, 표 목차와 그림 목차, 간지 |
| 기획보고서 | 기획보고서, 기획안, 추진계획(안), 행사 기획, 과제카드, 요약보고서, 이슈리포트, 브리핑자료, 가이드라인, 매뉴얼 등 | `init 작업폴더 --kind plan` | references/planning.md | 제안서와 같은 계위, 문서 제목 |

- (유형별 목적) 세 유형은 독자가 문서로 하는 일이 다름
    + (제안서) 협상에 의한 계약에서 심사위원이 발주처 사정의 이해도와 과업 수행 역량을 비교하여 수행 기관을 고르는 문서
    + (사전진단보고서) 과업 착수 전 진단 단계에서 발주처 담당자가 현황, 격차, 방향(안)을 확인하여 사전 협의와 내부 보고에 쓰는 문서. 최종보고서 체계를 갖추어 담당자가 최종 산출물을 미리 보는 초안을 겸함
    + (기획보고서) 결과물을 이용할 사람의 필요에서 출발하여 무엇을 어떻게 할지 실행 전에 정하는 문서. 이슈리포트, 가이드라인 등 간단한 형식은 기획의 판단 재료나 결과를 전달하는 문서
- 요청 문구로 유형이 정해지지 않으면 착수 질의에서 확인
- 산출 유형은 state.json에 기록. build와 check all은 기록된 유형으로 동작
- 세 유형 모두 이용 안내, 대화 응답, 준비, 작성 규범의 계위와 문장 규율, 조판, 렌더링 검수를 적용. 사전진단보고서와 기획보고서가 따르는 SKILL.md의 절과 생략하는 절은 각 참조 파일의 적용 범위 표가 정함
- 산출 형식은 착수 질의 답변으로 정함. 권장은 hwpx 또는 docx 중 1개. `build --format hwpx|docx|both`
    + (1개 권장 사유) 두 형식을 함께 산출하면 렌더링 검수와 결함 수정이 형식마다 반복됨. 이 반복이 컨텍스트를 소모하여 후반 단계의 작성과 검수 품질을 떨어뜨림
    + (둘 다 선택 시) 유저가 착수 질의에서 둘 다를 고르면 다음 응답에 위 사유를 1줄로 고지. 유저가 선택을 유지하면 `--format both`로 진행

## 이용 안내

- state.json이 없는 새 작업폴더로 착수하는 경우 첫 응답의 맨 앞에 아래 안내문을 문구 그대로 1회 표시. 표시 후 착수 순서를 그대로 진행

> **juja-builder 이용 안내**
> - 이 스킬이 만드는 문서는 유저의 검토와 수정을 전제로 한 초안
> - (착수 전 확인) RFP나 입력 자료의 전문과 원고 전체를 여러 단계에 걸쳐 다루는 고용량 작업
>     + 의도한 품질 확보를 위해 제공사별 최상위 등급 모델 사용 권장
>     + 토큰 사용량이 많아 요금제 한도와 API 비용의 사전 확인 필요
> - (작성 중 역할) 논지, 전략, 수치의 최종 결정은 유저가 수행
>     + 이 스킬의 역할은 판단 근거와 초안의 제시
> - (제출 전 검토) 제출 전 유저의 전면 검토 필요
>     + AI 모델은 사실, 수치, 논리에서 오류를 낼 수 있음
>     + 스킬에 수록된 제도, 법령, 방법론 정보도 오류나 개정 이전 내용을 포함할 가능성 존재
>     + 모든 내용은 공고 시점의 원문 대조 후 유저가 확정
> - (제출 후 책임) 이 스킬이 만든 문서의 사용에 따른 책임의 주체는 유저와 제안사
>     + 낙찰 여부는 이 스킬의 보증 범위 밖
>     + 스킬 제작자는 그 문서의 사용으로 생긴 손해와 법적 분쟁에 책임을 지지 않음

## 용어

- 용어의 뜻은 SKILL.md, 참조 파일, 스크립트 출력에 공통으로 적용. 원고에 쓰지 않는 어휘는 문장 규율 절과 lexicon.md 대체표가 정함

| 용어 | 뜻 |
|------|----|
| 유저 | 이 스킬로 제안서, 사전진단보고서, 기획보고서를 작성하는 사람 |
| 모델 | 이 스킬의 절차를 실행하는 AI |
| 작성자 | 설계 파일과 원고를 쓰는 주체. 모델과 유저를 포함 |
| 제안사 | 제안서를 제출하는 기관. 컨소시엄이면 참여 기관 전체 |
| 발주처 | 용역을 맡기고 결과물을 받는 기관. SKILL.md, 참조 파일, 설계 파일에서 쓰는 작업 용어. 원고에는 기관 실명을 사용 |
| 작업폴더 | `init`이 만드는 폴더. 설계 파일, 원고, 납품본, state.json을 보관 |
| 설계 파일 | 원고의 설계와 근거를 담는 작업폴더의 번호 파일. 00_제안전략서.md, 00_진단서.md, 00_기획설계.md, 01_요구항목표.md, 01_배점표.md, 02_섹션대장.md, 02_모듈총괄표.md, 02_스토리라인.md, 03_자료대장.md |
| 원고 | 작업폴더/원고/의 md 파일. build가 파일명 순으로 합본하여 납품본으로 조판 |
| 착수 질의 | 0단계에 유저에게 한 번에 묻는 질의. 항목은 절차 절 |
| 스켈레톤 | 스타일만 정의한 빈 hwpx 양식. 조판기가 이 양식 위에 원고를 조판. 기본 스켈레톤은 init과 build가 작업폴더/_양식/proposal.hwpx에 생성. docx는 스켈레톤 파일 없이 같은 설정부 정의로 스타일을 생성 |
| 산출 유형 | 제안서, 사전진단보고서, 기획보고서의 구분. `init --kind`가 정한 값을 state.json에 기록 |
| 산출 형식 | 납품 파일의 형식. hwpx, docx, 둘 다(both). 권장은 1개(사유는 산출 유형 절) |
| 과업 유형 | RFP 과업을 모듈 골격의 선택 기준으로 나눈 분류. 전략기획형, 사업기획형, 정보화계획형 등. 판별 신호는 과업 유형별 모듈 골격 절 |
| 심사위원 | 제안서의 점수를 매기는 평가위원회 위원 |
| 섹션 | 배점이 갈리는 최소 단위로 삼는 제안서의 절. ID는 장 번호와 절 번호의 결합(예시로 Ⅲ-2) |
| 결정 섹션 | 심사위원이 세부평가항목 1개의 점수를 매길 때 읽는 섹션 |
| 통제배점 | 섹션에 귀속된 배점의 합계. `ledger`가 배점표의 결정 섹션 열에서 산정. 결정 섹션이 여럿인 항목은 배점을 균등 분할 |
| 오리지널 파트 | 과업마다 새로 쓰는 절. 원고 파일명의 첫 숫자 3 또는 5. 섹션대장 유형 열의 값은 오리지널. 이 파트의 섹션을 오리지널 섹션으로 부름 |
| 공통 파트 | 회사자료.md 값으로 채우는 절. 원고 파일명의 첫 숫자 4 또는 6. 섹션대장 유형 열의 값은 공통. 이 파트의 섹션을 공통 섹션으로 부름 |
| 논증 절 | 판단문으로 주장을 전개하는 절. 배경 및 필요성, 추진전략, 제안의 특징 및 장점, 시사점 |
| 정리 절 | 사실과 구성을 정리하는 절. 과업 목적과 범위, 추진 프로세스, 현황 정리, 법령 목록, 추진체계, 일정 |
| 배경 | 제안 배경 및 필요성 절의 약칭 |
| 특장점 | 제안의 특징 및 장점 절의 약칭 |
| 과업 목적 | 과업의 결과로 발주처가 이르려는 상위의 상태 또는 방향. "왜 하는가"의 답. 문형, 수치 제한, 예시는 content-models.md 제안 범위 절 |

### 업무 개념

- 과업 판정과 원고 서술에 쓰는 기본 개념. 경영학과 행정학의 정의를 이 스킬의 용도에 맞춰 좁힌 뜻

| 구분 | 용어 | 뜻 |
|------|------|----|
| 작업 방식 | 기획 | 목표를 이루는 수단과 순서를 실행 전에 정하는 과정(Dror). 그 결과물이 계획 |
| 작업 방식 | 제안 | 고객이 가장 중시하는 몇 가지 기준에서 경쟁 대안보다 나은 해법과 그 근거를 제시하여 선택을 얻는 영업 행위(Anderson 외). 공공 용역은 협상에 의한 계약의 제안서 평가로 협상 대상자를 정함 |
| 작업 방식 | 연구 | 지식을 늘리거나 새 적용을 찾는 체계적 활동(OECD 프라스카티 매뉴얼). 이 스킬의 연구는 발주처의 판단 근거를 만드는 연구 과업(정책연구, 조사분석 등) |
| 작업 방식 | 컨설팅 | 조직의 문제 해결과 변화 실행을 돕는 독립적 자문. 과정은 착수, 진단, 실행 계획, 실행, 종료(Kubr) |
| 적용 영역 | 경영 | 조직의 목표를 이루려고 자원을 계획, 조직, 지휘, 통제하는 활동(Fayol). 경영전략, 조직진단, 공공기관 경영평가가 이 영역 |
| 적용 영역 | 정책 | 정부가 공공 문제를 두고 하기로 또는 하지 않기로 정한 행동 방침(Dye). 법령, 계획, 예산 사업으로 구체화 |
| 적용 영역 | 제도 | 사람과 조직의 행동을 제약하는 규칙과 그 집행 방식(North). 법령, 지침, 평가 체계, 심사 절차 등 |
| 추진 단위 | 전략 | 도달할 목표와 그에 이르는 선택. 하지 않을 일까지 정함(Porter). 기본계획, 중장기 전략, ISP처럼 계획을 세우는 과업은 모두 전략 수립 |
| 추진 단위 | 사업 | 목적을 가진 활동 묶음에 재원을 배정한 단위. 기업에서는 고객에게 가치를 파는 사업 단위, 재정에서는 프로그램, 단위사업, 세부사업의 예산 단위 |
| 목표 관리 | 목적 | 활동이 필요한 이유이자 도달하려는 상위의 상태나 방향. "왜 하는가"의 답. 과업 목적은 이 뜻을 과업에 적용한 용어 |
| 목표 관리 | 목표 | 목적에 이르려고 정한 구체적 도달 수준. 대상, 수준, 시점으로 특정. 달성 여부는 지표로 측정. 과업 목표는 이 뜻을 과업에 적용한 용어 |
| 목표 관리 | 성과 | 활동이 수혜자에게 낳은 변화. 산출과 구분되는 결과와 영향이 중심(OECD DAC). R&D 법령의 연구개발성과는 산출(제품, 지식재산권 등)까지 포함 |
| 목표 관리 | MBO | 목표를 기준으로 업무를 관리하는 방식(Drucker, 1954). 구성원은 목표 대비 성과로 스스로를 통제. 공공의 성과목표와 성과지표 관리도 같은 원리. 이 스킬에서는 전략기획(ISP 포함)의 기본 원리. 사업기획의 목표체계와 상위 정책 정렬에도 적용(methods.md 목표 설정 계통) |
| 판단 논리 | 문제 | 도달하려는 상태와 현재 상태의 차이. 메우는 방법이 바로 보이지 않아 분석이 필요한 상태 |
| 판단 논리 | 문제해결 | 차이를 메우는 원인과 해법을 찾는 절차. 이 스킬은 문제 정의에서 전달까지 7단계(McKinsey)를 적용 |
| 재원 체계 | R&D | 과학기술기본계획에 따라 과학기술 발전을 목적으로 추진하는 국가연구개발사업. 성과는 전용 법률(연구성과평가법)의 성과목표, 지표, 평가로 입증. 평가 결과는 예산 배분에 반영. 사업은 부처의 지원 사업, 과제는 그 안에서 연구개발기관이 협약으로 수행하는 단위 |
| 재원 체계 | 비R&D | 연구개발 밖의 정책 목표(복지, SOC, 산업 지원 등)를 위한 재정사업과 기관 사업. 성과는 재정사업 자율평가 등 공통 체계로 관리. 사업은 예산의 세부사업. 과제는 계획 문서의 추진과제. 과제의 뜻은 문서마다 다름. 용어는 R&D보다 유연 |

## 대화 응답

- 유저는 대화창에서 판단에 필요한 정보만 읽음. 응답은 파일 경로, 진행 단계, 유저 판단 항목, 오류 보고로 구성. 착수 첫 응답은 이용 안내 절의 안내문을 포함
- 응답에서 제외하는 내용
    + 유저 입력, RFP 내용, 파일 본문의 재서술 (02_스토리라인.md와 원고 포함)
    + 도구 호출과 작업 순서의 중계, 스킬 내부 용어와 규칙의 설명
    + 다음 작업의 예고, 작업 완료 자평, 요청받지 않은 추가 작업 제안(스토리라인 제시 시의 심화 선택지 1줄은 예외)
- 수정 결과는 바뀐 지점만 보고. 점검 결과는 PASS 건수, FAIL 건수, 미해결 항목만 보고
- 질문은 한 턴에 묶음. 합리적 기본값이 있는 항목은 기본값 명시 후 진행
- 응답 문체는 개조식 단문. 단계 완료 보고는 짧게 작성
- 유저에게 검토, 확인, 승인을 요청하는 파일과 납품 파일은 실행 환경이 제공하는 파일 전달 기능으로 전달. 작업폴더가 유저에게 보이지 않는 환경에서는 유저가 경로 안내만으로 파일을 열 수 없음
    + 주요 전달 시점은 2단계 승인 요청과 재제시, 원본 이미지 후보 확인, 6단계 납품(hwpx 또는 docx, 동봉 시 PDF), 유저가 파일을 요청한 때
    + 전달 기능이 지정 폴더의 파일만 전달하는 환경은 그 폴더에 사본 배치 후 전달. 작업폴더의 원본이 기준본
    + 전달 기능이 없는 환경은 파일 경로를 안내
- 파일은 필요한 범위만 읽음. 같은 파일을 반복해서 읽지 않음(1단계의 01_RFP원문.md 전문 읽기, 심층 검토의 원고 재읽기, 세션 인계 시의 읽기는 예외). 스크립트 stdout은 판정 요약만 확인
- 분량 저감을 이유로 오류 원인 보고, 수치의 출처, 유저 승인 절차를 생략하지 않음

## 전제

- 제안서는 채점표에 응답하는 문서. 배점이 갈리는 최소 단위를 섹션으로 삼음
- 낙찰을 가르는 요인은 실무 이해의 증거. 조사 대상 기관명, 자료명, 조사 규모, 사전조사 결과 표가 증거에 해당. 방법론 명칭에는 증거 기능이 없음
- 이면 니즈의 특정은 제안서를 RFP 요약과 구별하는 조건(표면 니즈와 이면 니즈의 정의는 용어 절)
- 분량은 구성 단위의 수에서 발생. 정성제안서의 일반적 구성에서 □ 1개는 ❍ 2-3개, 근거 줄 2개 이상, 표나 그림 1개로 대략 1쪽. 이 단위를 채우면 통상의 제안서 분량에 도달(계위 기호는 원고 계위 절)
- 단문 규율은 유지. 연결어미로 늘린 문장은 의미 관계가 흐려짐. 분량은 근거 줄과 표를 늘려 확보
- 심사위원은 RFP 워딩을 따라 채점. 핵심 워딩은 제안전략서의 핵심 워딩 사전에 수록. 원고의 출현 여부는 코드로 대조
- 수행부문은 통상 본문의 절반 이상을 차지
- 그림의 원천은 RFP와 유저 제출 문헌에서 추출한 원본 이미지와 발표자료 쪽의 도식 캡처. 도식과 차트를 코드(SVG, 파이썬)로 생성하는 작업은 범위 밖. 나머지 시각 요소는 표로 표현

- 의존성 설치를 다른 작업보다 먼저 수행. 로컬 환경은 가상환경 안에서 `--break-system-packages` 없이 설치. 최신 API 변경으로 스크립트가 실패하면 실패한 호출부만 최신 API에 맞게 수정
- 착수 순서는 아래로 고정. 렌더러 확보와 렌더 시험은 착수 질의보다 먼저 수행
    + 6단계는 원고와 점검 기록으로 컨텍스트가 가장 찬 구간. 이 시점의 렌더러 확보는 시도 축소와 조기 포기로 실패율이 높음. 착수 시점의 확보와 시험은 실패 원인을 해결할 시간을 남김
    1. 의존성 설치(위 pip 명령)
    2. 렌더러 확보(아래 1-3순위)
    3. `init 작업폴더`
    4. `selftest 작업폴더`로 표본 원고의 조판과 렌더링을 판정. PASS면 산출 PNG 1장에서 글머리, 밴드, 표의 표시를 확인. FAIL이면 다음 순위 렌더러로 이동 후 재실행
    5. `rfp` 변환과 착수 질의
- 2순위(소스 빌드)로 넘어가면 빌드는 세션과 분리된 백그라운드 프로세스로 실행. 빌드 중에는 3번과 5번(`init`, `rfp` 변환, 착수 질의)을 병행. 4번 `selftest`는 빌드 완료 후 실행
    + 1단계 진입 전에 `selftest` PASS를 확인. 빌드가 그때까지 끝나지 않으면 3순위 설치 후 soffice 경로로 PASS를 먼저 확보. 빌드 완료 후 rhwp로 `selftest`를 재실행
- `selftest` 판정은 state.json의 checks.render에 기록(엔진, 쪽수, 오류). 이 기록이 세션 인계와 6단계의 렌더러 판단 근거
- `selftest`는 같은 표본의 docx 조판과 LibreOffice 렌더링도 판정. 판정은 state.json의 checks.render_docx에 기록
    + docx 납품은 이 기록의 PASS가 조건
    + LibreOffice가 없으면 3순위의 apt 명령으로 설치
- 스킬 폴더가 읽기 전용인 환경에서 스크립트 수정이 필요하면 스킬 폴더 전체를 쓰기 가능한 경로에 복사. 이후 `<SKILL>`은 사본 폴더
- 동작 확인 환경은 Python 3.11-3.12, python-hwpx 6.x, python-docx 1.2.0, lxml, pillow, pdfplumber 0.11, pypdfium2 5.x, poppler 24.02, rhwp v0.8.6, LibreOffice 24.x. 설치는 최신 버전으로 수행. 이 기록은 버전 차이로 실패할 때 원인을 추적하는 기준
- 렌더러 1순위는 rhwp CLI(https://github.com/edwardkim/rhwp). 아래 절차로 GitHub 릴리스의 CLI 실행 파일을 직접 확보. npm 패키지(@rhwp/core, @rhwp/editor)는 라이브러리와 편집기 용도. CLI 확보 경로에서 제외. PyPI 등 다른 패키지 저장소의 같은 이름 패키지도 제외 대상. 2순위(소스 빌드)로의 이동 조건은 릴리스 확보 실패의 확인. 실행 환경의 권한 거부는 아래 rhwp 권한 거부 항목을 따름
    + (GitHub 저장소 연결) 세션에 GitHub 저장소를 연결하는 도구가 실행 환경에 있으면 첫 GitHub 접근 전에 호출. 인자는 소유자 `edwardkim`, 저장소 이름 `rhwp`를 각각 따로 전달. 도구 응답이 안내하는 접근 경로는 아래 절차에 반영. 도구가 없거나 호출이 거부되면 이 단계를 건너뜀
    + GitHub의 주소 체계와 페이지 구성은 바뀔 수 있음. 모델은 현재 상태를 확인하여 아래 순서로 릴리스를 확보
    + GitHub 주소는 웹 화면 경로와 파일 전달 경로로 나뉨. 네트워크 허용 목록을 쓰는 실행 환경에서는 웹 화면 경로(`releases/latest`, `releases/expanded_assets`, `api.github.com`)의 403 상황에서도 파일 전달 경로(`releases/download/<태그>/<파일명>`)와 git 프로토콜이 통과하는 경우가 있음
    + 1순위 실패는 4번 파일 전달 경로의 수신 실패로만 판정
    1. 기존 실행 파일(`rhwp --version` 동작 또는 `<SKILL>/scripts/rhwp/rhwp` 존재)이 있으면 버전을 아래 2번의 최신 태그와 대조. 최신이면 확보를 생략. 낮으면 아래 절차로 최신본 수신 후 교체. 특정 버전 지정을 유저가 요청한 경우에만 그 버전을 유지
    2. 태그는 `git ls-remote --tags --refs https://github.com/edwardkim/rhwp` 출력의 버전 태그 중 최고 버전으로 확인. git 접근이 막힌 경우에만 https://github.com/edwardkim/rhwp/releases/latest 리다이렉트의 최종 주소 끝에서 확인. 특정 버전이 필요하면 그 태그를 사용
    3. 자산 목록은 `curl -fL`로 받은 `https://github.com/edwardkim/rhwp/releases/download/<태그>/SHA256SUMS.txt`의 파일명 열에서 확인. 이 파일이 없으면 `releases/expanded_assets/<태그>`, GitHub API `/repos/edwardkim/rhwp/releases/tags/<태그>` 순으로 시도. API는 비인증 호출 한도(시간당 60회) 때문에 공용 IP에서 403이 자주 발생. 이 사유로 API를 마지막 순서에 배치. 릴리스 페이지 본문은 자산 목록을 늦게 불러옴. 이 본문은 자산 목록의 근거로 쓰지 않음
        + 최고 버전 태그에 릴리스가 없으면(SHA256SUMS.txt 404) 다음 버전 태그에서 재시도
    4. 자산 목록에서 현 플랫폼(OS, CPU)에 맞는 압축 파일을 선택. 파일명 패턴은 가정하지 않음. 선택한 파일을 `https://github.com/edwardkim/rhwp/releases/download/<태그>/<파일명>`에서 `curl -fL`로 수신. SHA256SUMS.txt가 있으면 `sha256sum -c`로 대조 후 압축을 해제. 불일치하면 확보를 중단
    5. 실행 파일은 실행 권한 부여 후 `<SKILL>/scripts/rhwp/`에 배치. 이 폴더에 쓸 수 없으면 `~/.local/bin`에 배치. 두 위치 모두 render가 자동 탐색. 다른 위치에 두면 `render --rhwp 경로`
    6. `rhwp --version`과 `rhwp export-pdf --help`로 동작을 확인. export-pdf가 없는 버전이면 `rhwp --help`에서 PDF 출력 명령을 확인
    + 확보한 실행 파일은 스킬을 다시 패키징할 때 포함하지 않음
- 2순위는 rhwp 소스 빌드. 파일 전달 경로의 자산 수신이 403이나 저장소 접근 거부로 막힌 환경에서도 git 프로토콜이 통과하는 경우가 있음. 릴리스 확보가 실패하면 3순위 전에 2순위를 시도
    + rhwp는 변경이 잦은 프로젝트. 빌드 방법은 `git clone`으로 받은 저장소의 그 시점 구성으로 판단
    1. 판단 재료는 저장소 루트의 빌드 매니페스트와 워크스페이스 구성, 툴체인 핀, CI 설정, 개발 문서
    2. CLI 바이너리와 PDF 내보내기 경로를 담은 타깃을 확인. 그 타깃만 빌드
    3. 빌드 시간을 줄이는 프로파일이나 피처 조합이 있으면 선택. 검수용 바이너리는 최적화 수준보다 완료 시간을 우선
    4. 산출 바이너리를 1순위 5번의 위치(render 자동 탐색 위치)에 배치. 1순위 6번의 방법으로 동작을 확인
    + 클론 용량은 수 GB에 이를 수 있음. 저장소에는 빌드와 무관한 대용량 자료가 섞여 있을 수 있음. 클론 전에 여유 공간을 확인. 용량이 부담되면 이력 없는 부분 클론(blob 지연 수신과 sparse checkout)으로 빌드에 필요한 경로만 받음
    + 부분 클론에 포함할 경로도 저장소 구성으로 판단. 재료는 워크스페이스 멤버 경로, 매니페스트가 경로를 명시한 타깃 파일, 소스가 빌드 시점에 불러오는 파일, 컨테이너 빌드의 제외 목록
    + 빌드가 '파일 없음'으로 실패하면 오류에 나온 파일만 추가로 받음. 그 파일이 큰 폴더 안에 있는 경우에도 해당 파일 1개만 받음
    + 기본 브랜치의 최신 커밋은 개발 중 상태일 수 있음. 릴리스 페이지가 막힌 환경에서도 `git ls-remote --tags`로 태그 목록은 확인 가능. 최신 릴리스 태그를 우선 빌드. 태그 빌드가 실패하면 기본 브랜치로 재시도
    + 빌드는 오래 걸릴 수 있음. 명령 1회의 실행 시간에 상한이 있는 실행 환경은 빌드를 세션과 분리된 백그라운드 프로세스로 실행. 명령 종료 시 하위 프로세스를 정리하는 실행 환경도 같음. 분리한 빌드는 로그를 주기적으로 확인. 중단된 빌드는 같은 명령의 재실행으로 이어서 진행
    + 빌드 후 클론 폴더와 빌드 산출 폴더는 삭제해도 무방
    + git 접근 거부나 빌드 실패 시 3순위로 이동. 사유는 최종 보고에 기재
- 3순위는 LibreOffice와 H2Orestart. Debian 계열 기준으로 `apt-get update` 후 `apt-get install -y --no-install-recommends libreoffice-writer libreoffice-java-common default-jre-headless libreoffice-h2orestart fonts-nanum poppler-utils`. 이후 `render --engine soffice`
- rhwp 권한 거부는 실행 환경의 권한 검사가 rhwp를 받거나 실행하는 명령(태그 조회, 내려받기, 클론, 빌드, 실행)을 거부한 경우. 거부가 나오면 rhwp 확보를 그 자리에서 멈춤. 이어서 유저에게 rhwp 내려받기와 실행의 허용 여부를 질의. 답을 받기 전에는 3순위 확보, `selftest`, 1단계 이후 작업을 진행하지 않음
    + (판정) 명령이 실행되지 않고 실행 환경의 거부 응답만 돌아오면 권한 거부. 명령 실행 뒤의 403, 연결 오류, 저장소 접근 거부는 네트워크 실패로 보고 위 순위 이동 규칙을 적용
    + (질의 이유) 권한 거부는 유저의 허용으로만 풀림. 질의 없이 3순위로 넘어가면 유저가 허용할 기회가 사라짐
    + (중단 범위) 같은 rhwp 코드를 다른 경로(2순위 소스 빌드, 다른 내려받기 도구)로 받는 시도도 중단. rhwp와 무관한 착수 순서 항목(`init`, `rfp` 변환)은 계속 진행
    + (질의 시점) 착수 순서 2번의 거부는 착수 질의 목록의 맨 앞 항목으로 질의. 이후 단계의 거부는 거부 시점에 질의
    + (답에 따른 진행) 허용하면 1순위부터 다시 확보. 허용하지 않거나 답이 없으면 2순위 없이 3순위로 `selftest` 진행
- 세 경로가 모두 실패하면 render를 생략. 생략 사실과 사유는 착수 질의 턴에 유저에게 고지. 최종 보고에도 같은 내용을 기재
- 발표자료 변환 경로의 pptx 입력은 LibreOffice(`soffice`)로 PDF 변환. 설치는 `apt-get install -y --no-install-recommends libreoffice-impress fonts-nanum fonts-noto-cjk`. 한글 글꼴이 없으면 변환본의 줄바꿈과 도식 배치가 원본과 달라짐. pdf 입력은 LibreOffice 없이 처리
- 렌더링 검수에는 나눔 글꼴이 필요. Debian 계열은 `apt-get install -y --no-install-recommends fonts-nanum`. 글꼴이 없으면 근사 렌더러가 대체 글꼴을 사용. 이 경우 글자 폭과 줄바꿈이 납품본과 달라짐
- poppler-utils는 RFP pdf 입력(pdftotext)과 페이지 PNG 산출(pdftoppm)에 필요. pdfplumber는 발표자료 pdf의 본문과 표 추출에 필요. pdfplumber와 함께 설치되는 pypdfium2는 쪽 PNG, 도식 캡처, pdf 원본의 이미지 추출에 필요

- `build`는 `check all` PASS 기록이 없으면 중단. PASS 이후 원고, 02_모듈총괄표.md, 라벨 파일이 바뀌어도 중단(check all 재실행으로 해소). `--force`는 시험 조판과 점검 절의 오판 처리에만 사용

    + (웹검색 불허) 유저가 제공한 낙찰 결과만 기입. 나머지 행의 `[확인]`은 유저 질의로 해소
    + (미확인 유형) 모든 탐색 경로를 수행해도 기관이 확인되지 않은 유형은 `[확인]`을 붙여 유저 질의로 해소
- 스토리라인 필드의 3줄(배경 및 필요성, 추진전략, 모듈별)은 방향을 잡는 초안. 2단계의 02_스토리라인.md가 이 3줄을 절별 메시지와 □ 판단문으로 전개. 두 파일이 어긋나면 02_스토리라인.md의 승인본을 기준으로 전략서를 갱신
- 추진전략은 과업 특성과 위험 요인에서 핵심성공요인을 거쳐 도출. 도출 순서는 제안전략서에만 기록. 본문에는 전략, 그 전략이 해소하는 위험, 전략이 확보하는 가치를 서술
    + 전략은 이 과업이 왜 어려운가에서 도출. 발주처가 이 과업을 하는 이유(배경의 문제)는 과업 전체가 답함. 배경의 문제에서 도출한 전략은 Module 목록을 전략 이름으로 바꿔 쓴 결과가 됨
    + (과업 특성) 과업이 끝내야 하는 범위와 다뤄야 하는 대상의 성질. RFP가 정한 과업 내용, 제도 절차, 준수 의무, 제약 조건도 이 열에 기입. 의무는 모든 입찰자가 수행하는 전제. 의무를 달성하는 차별화 방안은 전략 열에 기입. 예시로 계획에서 구축 요건까지 끝내야 하는 범위, HWP와 PDF 위주의 비정형 자료, 망분리 보안 체계, 분야별로 다른 기술 특성, 제도가 정한 평가 일정, 이해관계자의 수, 과업 기간
    + (위험 요인) 과업 특성 때문에 결과물이 어긋날 수 있는 지점. 예시로 문서 텍스트 추출 품질 저하, 민감 자료의 외부 모델 전송 불가, 기술 분야별로 다른 지표 해석, 평가 제출 시한 안의 성과 근거 누락, 현장 수요와 동떨어진 과제, 수립 이후 계획의 내부 사장
    + (핵심성공요인) 위험을 넘기 위해 결과물이 갖춰야 할 조건과 판별 기준 1줄. 예시로 "실효성 있는 과제 발굴"의 판별 기준은 "실제 업무를 줄이는 체감형 과제 선정"
    + (확보하는 가치) 성공요인을 충족할 때 과업과 결과물이 발주처에 주는 가치. 해소하는 위험과 짝으로 기입. 예시로 "오답 불신을 해소하는 신뢰성", "민감 자료의 외부 유출을 막는 안전성". 위험 없이 가치 낱말만 적은 항목은 어느 과업에나 붙는 문구가 됨
    + (추진전략) 성공요인을 확보하는 특화 방안
        + (결과물 설계 원칙) 결과물을 어떤 원리로 만드는가. 예시로 지역 보유 역량 기반의 특화, 기술에서 정책과 성과로 이어지는 단계별 대응, 근거 제시형 답변, 비교군을 둔 성과 분석
        + (수행 활동) 과업을 어떤 활동과 운영으로 수행하는가. 예시로 기술 특성별 분과 위원회, 분과별 지표 사전테스트, 착수 초기의 이슈별 산출물 초안, 협의체 자문과 수요조사의 결합, 산출물 활용 설명회
    + (성립 조건) 추진전략은 이 과업의 효과적 수행을 위해 특화와 차별화를 갖춘 방안. 특화는 과업 대상의 특성에 맞춘 설계. 차별화는 RFP와 제도가 요구하는 수준 위에 제안사가 더하는 설계
        + (의무 삭제 시험) 판단문에서 RFP 과업 내용, 제도 의무, 제약 조건의 준수를 지웠을 때 남는 방안이 전략. 남는 방안이 없으면 의무의 재진술
        + 수행 활동은 활동의 설계를 과업 난점에 맞춰 특정할 때 전략이 됨. 예시로 분과를 가르는 기준, 사전테스트의 대상과 판정 항목, 산출물 초안의 공유 시점과 참여 주체
- 발주처가 얻는 성과는 1줄 스토리라인과 절별 메시지의 재료. 스토리라인 필드에 기입
    + 성과는 과업 이후 발주처에게 일어나는 변화. 예시로 상급 기관 심의 대응, 예산 반영, 제도 시행, 후속 사업 착수, 이행 부서의 합의
    + 산출물은 성과에 이르는 수단. 성과 자리에 산출물의 제출을 적으면 보고서 납품으로 끝나는 제안으로 읽힘
    + 성과는 누구의 무엇이 언제 어떤 상태가 되는지로 특정. 재료는 이면 니즈 가설의 발주 사정과 설득 대상
    + 대상, 시점, 상태의 특정은 성과의 구체성을 판별하는 점검 기준. 시점 값은 설계 재료로만 사용
    + 성과를 추진전략 판단문의 종결로 쓰지 않음. 전략과 제도 사건 사이의 거리가 멀면 그 사이를 일정과 협의 같은 작성자의 계획으로 채우게 됨
- 핵심 워딩 사전은 RFP 과업 항목의 명사구를 원문 표기로 수록. 제안서 표기 열에 같은 표기를 기입하면 띄어쓰기 변형까지 탐지
- 가격 방향은 예산 상한 대비 투찰 구간과 판단 근거만 기재

## 골격 설계

### 장 구성

- 장과 절의 이름, 순서, 번호는 RFP의 지정 목차와 제안서 작성 지침을 그대로 사용. 목차 지정이 없으면 평가항목의 순서를 참고로 아래 표를 적용
- 지정 목차의 절마다 유형과 내용 모델을 02_섹션대장.md에 기입. 유저 확인은 2단계 승인에서 받음
    + (유형) 과업마다 새로 쓰는 절은 오리지널. 회사자료.md 값으로 채우는 절은 공통
    + (내용 모델) 절이 답해야 하는 평가항목과 요구 내용으로 판단. 발주 배경과 필요성은 배경 모델, 과업 목적과 범위는 제안 범위 모델, 제안사의 역량과 차별성은 특장점 모델, 수행 전략과 방법론의 적용은 추진전략 모델, 과업별 수행 방안은 Task 서술 표준을 적용
    + 지정 절 1개가 두 모델에 걸치면 모델별 항(###)으로 작성
    + 해당 모델이 없는 절(교육훈련, 기술이전, 사회적 가치 등)은 RFP 요구 문장을 □의 재료로 삼아 분량 구성 단위로 작성
- 섹션 ID는 지정 목차의 장 번호와 절 번호를 사용(정의는 용어 절)

| 순서 | 장 | 절 이름 | 유형 | 기본 파일명 |
|------|----|---------|------|-----------|
| Ⅰ | 제안 개요 | 제안 배경 및 필요성(31), 제안 범위(32), 추진전략(33), 제안의 특징 및 장점(34) | 오리지널 | 3x |
| Ⅱ | 제안사 일반현황 | 일반현황, 조직과 인원, 주요 사업실적(41) | 공통 | 4x |
| Ⅲ | 사업 수행부문 | 과업 추진체계(51, 독립 절인 경우), 수행방법과 프로세스, 세부 수행내용(52 이후) | 오리지널 | 5x |
| Ⅳ | 사업 관리부문 | 수행조직 및 업무분장(61), 추진일정, 업무보고, 산출물 관리, 보안, 사후관리(62) | 공통 | 6x |

- 원고 파일명의 첫 숫자는 판정 유형. 3은 논증과 개요 성격의 오리지널, 4와 6은 공통(`check fill` 대상), 5는 수행 방안 오리지널(`check density` 대상). 지정 목차에서도 절의 유형에 맞는 숫자를 사용
    + build는 파일명 순으로 합본. 목차를 지정한 과업은 전 원고의 파일명 앞에 목차 순서대로 순번 접두를 부여(`10-31_사업이해.md`, `20-52_세부수행방안.md`, `40-41_제안사현황.md`). 판정 유형은 순번 접두 뒤의 첫 숫자로 판별
    + 목차 지정이 없는 과업은 순번 접두 없이 위 표의 기본 파일명을 사용
    + SKILL.md와 참조 파일의 파일 번호(31-34, 41, 51, 52, 61, 62)는 기본 파일명. 지정 목차에서는 같은 내용 모델이나 템플릿을 적용한 파일을 가리킴
- 장 제목(`# 제목`)은 원고에 직접 기입. 장마다 그 장에 속한 원고 파일 중 파일명 순으로 첫 파일의 첫 줄에 1회 기입
    + 템플릿(41, 61, 62)의 장 제목, 절 제목, 절 순서는 지정 목차에 맞춰 교체. 절이 다른 장으로 갈리면 파일을 나눔(유형 숫자는 유지)
- 통제배점 5점 이상인 공통 성격의 절(연구책임자 전문성, 보안 관리 등)은 오리지널로 분류. 공통 자료를 쓰는 경우에도 3단계 밀도로 작성
- RFP가 요약 장(제안 개요)과 본문 장(추진 전략)을 따로 지정하면 요약 장에는 전략명과 1줄 요지를 둠. 추진전략 모델의 전개는 본문 장에 둠
- RFP가 약어표나 참고문헌 목록을 요구하면 RFP가 지정한 위치에 표로 둠. 지정이 없으면 마지막 장의 끝에 둠
- 번호 계위는 장(Ⅰ.), 절(1.), 항(가.), 목(1))까지. 논점이 늘면 □ 계위로 흡수. RFP 지정 목차의 번호 형식이 다른 경우(가. 다음 (1) 등)에도 항 아래 계위는 원고 계위 절을 적용

### 추진체계의 배치

- 추진체계(수행체계)는 Module과 Task의 수행, 연계, 관리 방식을 보이는 내용. 주체는 발주처, 제안사, 이해관계자. 추진전략과 같은 HOW의 역할
- 추진체계는 수행조직과 소재가 겹침. 수행조직은 인력, 참여율, 업무분장을 다루는 행정 서술. 추진체계는 같은 소재를 회의체 운영, 발주처 협의, 모듈 간 연계의 실무 관점에서 서술
- 배치는 RFP 목차와 평가항목을 근거로 모델이 판단. 판단 결과는 2단계의 02_섹션대장.md에 반영. 유저 확인은 2단계 승인에서 받음
    + RFP가 추진체계를 별도 항목으로 요구하면 독립 절(51)로 작성
    + RFP가 요구하지 않으면 추진전략 절(33)이나 수행조직 절(61)에 통합
    + 기획위원회와 분과위원회를 운영하는 대형 기획 과업(예비타당성조사 대응 등)은 추진체계의 비중이 큼. 독립 절을 우선 검토
- 추진체계 내용은 어느 배치에서도 한 절에 1회 배치. 수행체계 표, 회의체 운영(안) 표, 위원 후보(안) 표는 그 절에 둠. 다른 절은 그 절의 고유 내용만 서술
    + 회의체가 추진전략의 수단이면(기술 특성별 분과 위원회 등) 추진전략에는 구성 기준과 확보하는 가치를 서술. 회차, 시기, 안건의 운영(안) 표는 추진체계 내용을 담은 절에 둠

### 배경 골격

- 배경 및 필요성은 WHY의 절. 발주처가 이 과업을 왜 지금 필요로 하는지를 서술. 제안사의 보유 역량(WHAT)과 수행 방식(HOW)은 쓰지 않음
- 배경의 골격은 SCQA 또는 SCR. S, C, Q, A 단의 정의는 바바라 민토(Barbara Minto)의 피라미드 원칙에서 서론을 구성하는 방식을 따름. SCR은 Q를 생략한 채 해결(R)을 바로 제시하는 실무 변형. 단을 생략하면 일반론으로 읽힘
    + (S 상황) 독자가 이미 아는 사실이나 이견 없이 동의할 주제 관련 사실
    + (C 전개) 그 상황에서 발생하여 질문을 일으키는 변화나 문제
    + (Q 질문) 전개가 독자의 마음에 일으킨 질문
    + (A 답변) 그 질문의 답. 제안 범위와 추진전략으로 연결
    + (R 해결) SCR의 마지막 단. Q 없이 전개의 해결을 제시
- 단의 재료는 00_제안전략서.md의 발주처 니즈, 외부환경, 제안 전략에서 과업마다 도출
- 배경 전체는 바깥에서 안으로 좁히는 순서를 권장. 서두를 좁은 주제로 시작하면 과업의 필요성이 상위 환경과 이어지지 않음
    + 진입 순서는 거시환경(정책, 기술, 사회), 분야와 산업의 여건, 발주처 내부의 사정
    + 포함할 단계는 과업에 맞게 선택. 포함한 단계의 순서는 유지
- □ 제목과 괄호 소제목은 과업의 언어로 작성. 골격 명칭, 단 이름, "과업의 답"과 "전제조건" 같은 골격 언어는 설계 언어(용어 절)
- 전개형(사업기획, 정보화계획, 전략기획)은 S와 C를 여러 논점으로 전개
- 압축형(성과분석, 경영평가 대응, 조직과 인사, 문제해결)은 S와 C를 각 1-2개 논점으로 둠. 논점마다 구성 단위 하한은 채움

### 모듈총괄표

- 작업폴더 루트의 02_모듈총괄표.md에 아래 표를 작성. 이 파일은 섹션대장, 스토리라인과 같은 2단계 설계 산출물. 표의 원본은 이 파일 1곳

    + 추진전략 절의 메시지는 전략들이 확보하는 가치를 묶어 결과물을 수식하는 문장. 예시로 "차별성, 혜택, 실현가능성을 갖춘 OO 기본계획 수립", "전문성과 실효성을 확보한 진흥전략 및 실행계획 수립"

    + 수단이 활동 이름(진단, 시범 적용, 자문위원회 운영)에 그치면 Module이나 추진체계의 반복. 수단이 결과물 설계 원칙이면 원칙을 수단 자리에 씀. 수단이 수행 활동이면 활동의 설계(구성 기준, 대상, 시점)를 씀. 예시로 "자문위원회를 운영"은 "기술 특성별 분과 위원회 구성으로 지표의 분야별 타당성을 확보"로 작성

    + 제도나 RFP가 정한 제출 시한, 준수 의무, 제약 조건은 모든 입찰자의 전제. 판단문은 그 전제를 달성하는 특화 방안이나 그 전제 위에 더하는 방안으로 씀. 예시로 "부처 대응일정 준수"는 "대상사업별 근거자료 선행 정리로 부처 평가 일정 내 대응을 확보"로, "보안 규정 준수"는 "자료 등급별 처리 경로 분리로 국가 망 보안체계 안에서 생성형AI를 활용"으로 작성. 뒤 문장은 목표(일정 내 대응, 국가 망 보안체계)를 지운 뒤에도 수단(근거자료 선행 정리, 처리 경로 분리)이 남음
    + 시점을 고려한 설계는 수단 쪽에 담음. 예시로 "[기관명]의 기획 일정에 맞춘 시범 적용으로 현업 문서에서 검증한 활용 방안을 확보"처럼 발주처 일정과의 연동을 방식의 성격으로 표현

    + 특장점 판단문은 제안사의 보유 사실을 쓰는 자리. 주어는 제안사. 종결은 보유 사실로 맺음
    + 배경 판단문은 발주처와 그 상위 환경의 사정을 서술. 주어는 발주처나 상위 환경의 주체와 현상
- 제시 전에 아래 항목을 자체 점검. 어긋난 행은 수정 후 제시
    + 배경 판단문이 거시환경에서 발주처 내부 순서로 좁혀짐(권장)
    + 제안전략서 도출 표의 위험 요인마다 답하는 전략이 추진전략 표에 존재
    + 추진전략 판단문에 Module 명칭과 활동의 반복이 없음. 전략 표 삭제 후에도 모듈총괄표가 같은 내용을 전달하면 반복
    + 제안전략서의 차별화 포인트마다 특장점 판단문과 추진전략 판단문이 존재. 전략서에 없는 강점은 판단문에 없음
    + 이면 니즈 가설마다 답하는 Module이나 Task가 수행부문 표에 존재
    + 추진전략 표의 가치 열이 행마다 해소하는 위험과 짝을 이룸. 가치 낱말만 있는 행은 없음
    + 1줄 스토리라인과 절별 메시지의 성과가 대상, 시점, 상태로 특정됨. 산출물의 제출로 끝나는 문장은 없음
    + 추진전략 판단문 열에 완료 시점의 선언(어느 연도나 보고 시점까지 무엇을 끝낸다는 문장)이 없음. 판단문만으로 수행 방식이 드러남
    + 추진전략 판단문에서 RFP 과업 내용과 제도 의무를 지운 뒤에도 특화 방안이 남음
    + 절별 메시지 표가 섹션대장의 오리지널 섹션 전 행을 포함. Module과 Task 명칭이 모듈총괄표와 동일
- 제시는 한 턴. 02_섹션대장.md, 02_모듈총괄표.md, 02_스토리라인.md를 파일 전달 기능으로 전달(대화 응답 절). 유저는 파일 검토 후 수정 사항을 지시
    + 모듈총괄표에 적용한 장표 방식도 같은 턴에 안내. 유저가 다른 방식을 고르면 지시 줄을 교체
    + 확인 요청 항목은 3개 이내로 명시. 이 항목이 유저의 검토 대상을 좁힘. 예시로 "배경 C의 두 번째 논점을 감사 지적으로 볼지 제도 신설로 볼지"
- 수정 요청은 02_스토리라인.md에 반영. Module과 Task의 명칭, 순서, 개수가 바뀌면 모듈총괄표, 섹션대장, 요구항목표의 배치 섹션 열을 함께 갱신. 갱신 후 `ledger`와 `check rfp`를 재실행
    + 재제시는 바뀐 파일을 다시 전달. 응답에는 바뀐 행의 위치(절, 순서)만 안내
- 유저가 승인하면 파일 상단 (승인) 줄에 일자와 범위를 기입. 예시로 `- (승인) YYYY-MM-DD 기본 깊이 전체, Module 2는 심화`
- 승인 이후의 변경 규칙
    + 판단문의 의미 변경, 추가, 삭제, 순서 변경은 유저 재확인을 거침. 반영 순서는 02_스토리라인.md가 먼저, 원고가 다음
    + 글자 수 상한 맞춤과 `check tone` 지적 어휘의 교체처럼 의미가 같은 표기 다듬기는 재량. 02_스토리라인.md에 같은 표기로 반영. 해당 단계의 완료 보고에 1줄 기재
    + 승인 이후 Module과 Task 명칭을 바꾸면 어조 판정 화이트리스트의 원천 변경에 해당. 유저 지시가 있을 때만 `check tone --reset-whitelist`
- 심층 검토의 (이면 니즈 대응)과 (절 경계) 항목은 원고와 02_스토리라인.md의 대조로 확인

- SKILL.md와 참조 파일의 계위 호칭은 원고 표기(□, ❍, 하이픈, ․, ※). 조판 결과의 기호는 스켈레톤의 글머리 정의가 정함

- 원고에 코드블록 펜스(백틱 3개)를 쓰지 않음. `check tone`이 FAIL로 색출. 참조 파일 예시의 펜스는 예시 범위의 표시
- `(단위: )` 줄은 캡션과 표 사이. 수치 표에만 부여
- 출처 줄 `※ 출처: ` 또는 `출처: `는 표와 그림 바로 뒤. 외부 데이터 표와 외부 그림에만 부여

    + 각주 라벨은 원고 파일 안에서 고유하게 씀. build가 파일별로 라벨을 구분하므로 다른 파일과 같은 번호는 허용

- 셀 값 `^`는 위 셀과 세로 병합. `<`는 왼쪽 셀과 가로 병합. 셀 개행은 `<br>`. `---` 단독 줄은 쪽 나눔

### □ 제목의 문체

- 항(가.) 이상의 계위는 키워드형 명사구. 문장형 메시지는 □ 이하 계위에 배치
- □는 키워드형과 문장형(명사형 종결 메시지 1줄) 중 절의 성격에 맞는 쪽을 선택. 같은 항 안에서 한쪽으로 통일. 항이 없는 절은 절 단위로 통일
    + 논증 절(배경, 필요성, 시사점, 추진전략, 특장점)은 문장형. 예시로 "정부는 공공부문 AI 도입의 실행력 제고를 위한 제도적 여건을 마련"
    + 정리 절(과업 목적과 범위, 추진 프로세스, 현황 정리, 법령 목록, 추진체계, 일정)은 키워드형. 예시로 "과업 범위", "정책동향", "수행 조직"
- 괄호 소제목은 ❍와 하이픈에만 붙임
- □ 문단은 글머리 자동 정렬(내어쓰기 0)로 조판. 둘째 줄은 첫 줄의 본문 시작선에 맞춰짐. ❍와 하이픈도 같은 정렬. ․와 ※는 기호를 본문 글자로 표기. 정렬은 스켈레톤의 내어쓰기가 맞춤
- 계위별 글자 수 상한은 references/content-models.md 분량 구성 단위 절의 줄 상한 표를 따름. 넘친 문장의 해소 방법은 분할 후 하위 계위 추가 또는 표 전환. `check volume`이 초과를 경고
- □ 아래에는 ❍ 서술을 1개 이상 둠(오리지널 파트의 ❍ 하한은 분량 구성 단위 절). □는 문단의 머리. ❍ 없는 □는 헤더만 있는 마크다운과 같은 결함. 표와 그림은 그 ❍ 뒤에 배치
    + □ 바로 아래에 표만 두는 형태도 결함. 표 앞에는 표의 요지를 담은 ❍ 1개를 배치
    + 공통 파트(4, 6)를 포함한 전 원고에서 `check volume`이 □ 단독과 □ 직후 표를 FAIL로 판정
- ❍는 □의 논점을 구성하는 주장. 하이픈은 그 주장을 뒷받침하는 근거. 짝이 맞지 않으면 하이픈을 ❍로 올리거나 삭제
- Module 도입부와 Task는 □ 없이 밴드 아래에 라벨 ❍를 바로 둠. 구조는 Task 서술 표준 절

### 괄호 소제목

- 괄호 소제목은 항목의 이름을 본문보다 먼저 보이는 표지. 문장 첫머리가 드러내지 못하는 이름을 먼저 보여줄 때만 정보가 됨
- 붙일지는 그 항목이 형제 항목, 상위 항목과 맺는 관계로 판단. ❍와 하이픈에 같은 기준을 적용
    + (나열) 상위 항목이 가리키는 대상을 이름 있는 구성요소로 하나씩 펼친 형제 묶음. 예시로 등급, 단계, 대상 구분, 전략, 평가 요소. 형제 전체에 괄호 소제목을 붙임. 독자는 이름만으로 묶음의 구성을 파악. 문장 첫머리에 같은 명사가 있으면 그 명사를 괄호 소제목으로 옮김. 문장의 같은 명사는 삭제
    + (논증) 상위 주장을 뒷받침하는 사실, 수치, 사례, 인용의 형제 묶음. 문장의 주어(기관명, 제도명, 자료명)가 항목의 성격을 이미 보여줌. 이 묶음은 괄호 소제목 없이 씀
    + (요약) 주어가 주제를 대신하지 못하는 긴 논증 항목. 주제를 괄호 소제목으로 먼저 제시
- 나열 묶음은 형제 전체에 붙임. 일부만 붙이면 독자가 붙은 항목과 빠진 항목의 차이를 찾게 됨. 나열에 속하지 않는 줄(묶음 전체의 활용처, 부기)은 괄호 소제목 없이 묶음 끝에 둠
- 괄호 소제목마다 삭제 시험을 거침
    + 괄호 소제목을 지운 줄에서 잃는 정보가 없으면 지움
    + 괄호 소제목의 낱말이 같은 줄 본문에 다시 나오면 되풀이. 나열 묶음은 본문의 같은 낱말을 지움. 그 밖의 줄은 괄호 소제목을 지움. 예시로 논증 줄인 "(활용 기준) OO위원회는 데이터 활용 기준을 개정"은 괄호 소제목을 지움
    + 한 쪽 단위 원고에서 거의 모든 줄에 괄호 소제목이 있으면 논증 묶음에 붙은 괄호 소제목의 혼입 여부를 확인
- (설명), (내용) 같은 무의미한 괄호 소제목과 같은 괄호 소제목의 반복은 쓰지 않음
- 정해진 세트로 쓰는 라벨(Task의 (목적), (분석 대상), (산출물) 등)은 이 판단의 대상에서 제외. 세트의 구성과 적용은 references/methods.md 공통 표준의 Task 유형 절을 따름
- 아래 첫 예시에서 첫 ❍의 하이픈은 평가 요소의 나열. 이 하이픈에는 괄호 소제목을 붙임. 둘째 ❍와 그 하이픈은 판단문의 논증. 이 줄은 괄호 소제목 없이 씀. 둘째 예시는 ❍ 아래 하이픈이 등급 나열인 경우. 원고의 `-` 줄은 ❍로, 들여쓴 `+` 줄은 하이픈으로 조판

    + (평가 대상) 행정업무 자동화, 대민 상담, 정책 분석 영역의 도입 사업

### 분량 구성 단위

- 분량은 단위의 수로 만듦. 하한, 채움 방법, 하한 미달 시의 추가 순서는 references/content-models.md 분량 구성 단위 절
- □ 1개는 ❍ 2개 이상, 근거 줄(하이픈, ※) 2개 이상, 350자 이상. Task 1개는 표 1개 이상(원본에서 채택한 그림도 인정), 900자 이상. `check volume`은 ❍ 수 미달과 Task의 표와 그림 부재를 FAIL로 판정. 근거 줄 수와 글자 수 미달은 경고. 수치의 원천은 proposal.py 설정부 상수
- 개수 범위는 절(##)이나 항(###) 안의 □ 2-4개(5개 이상이면 항으로 묶음), □ 아래 ❍ 2-4개, ❍ 아래 하이픈 1-3개(4개 이상이면 표로 전환). 각 범위의 최댓값이 상한
- Module은 3-6개, Task는 모듈당 2-6개. 개수를 본문에서 선언하지 않음
- 특장점 5-10쪽, 추진체계 2-3쪽(독립 절인 경우)은 구성 단위를 채우면 도달하는 통상 범위

### Task 서술 표준

- Module과 Task는 밴드가 제목. 밴드 바로 아래에는 □ 없이 라벨 ❍를 둠
    + Task 밴드 아래에 □를 두면 형제 없는 단계가 생김. 밴드명, □, (목적)도 같은 내용을 되풀이함
    + 모듈 도입부도 밴드 아래에 ❍를 바로 둠. Module과 Task의 구조가 같아야 두 목적 ❍가 각 밴드의 항목으로 읽힘
- 한 단계에는 한 종류의 항목만 둠
    + (❍) Task의 속성을 밝히는 라벨 줄. 라벨 세트는 methods.md 공통 표준의 Task 유형 절
    + (하이픈) 그 라벨의 내용. 대상 목록, 방법의 단계, 기준, 산출물 구성, 표가 말하는 결론
    + 발견 사실과 표의 결론은 하이픈 단계에 둠. ❍ 단계에 두면 독자는 Task의 속성이 하나 더 있다고 읽음
- 모듈 도입부는 목적과 추진방안을 서술하는 ❍ 2개로 시작(소제목은 절 안에서 통일). 목적의 정의는 methods.md 공통 표준의 모듈과 Task의 목적 절. 이어서 모듈 개요표를 배치. 개요표는 전 모듈에서 같은 양식. 캡션 아래 `(폭: 모듈개요)`로 폭을 통일. Task 수가 다른 모듈의 개요표는 열 수가 같은 표끼리 통일됨
    + 열은 Task. 행은 추진과정, 활용자료, 산출물의 3행이 기본
    + (추진과정) Task 안의 수행 단계 2-4개를 순서대로 셀 글머리(`◦ 단계<br>◦ 단계`)로 기재. "조사 및 분석" 같은 한 줄 요약은 단계로 인정하지 않음
    + (활용자료) 자료명과 건수를 실명으로 기재
    + (산출물) 산출물 명칭을 기재
    + 세 행 모두 셀 항목이 2개 이상이면 셀 글머리로 나열. 기준은 원고 계위 절의 표 셀 규칙
    + 개요표의 단계, 자료, 산출물은 아래 Task 본문의 라벨 서술과 일치
- Task 유형(분석 중심, 도출 중심), 유형별 라벨 세트, (산출물) 라벨의 서술 범위, 제출 시점의 기재 위치는 references/methods.md 공통 표준의 Task 유형 절이 단일 원천
- Task 1개는 기본 서술과 채움본으로 구성. 채움본은 표가 뒷받침하는 라벨 아래에 둠. 표 앞에는 그 라벨 아래 하이픈 1개로 표의 결론을 먼저 서술. 상세는 content-models.md Task 서술 절
    + 분석 중심 Task는 대상의 현재 상태를 밝힘(문헌과 자료 조사, 인터뷰와 설문, 진단과 프로세스 분석, 데이터 분석). 채움본은 분석 방법에 맞는 표 2개 이상. 예시로 대상 실명 목록표, 사전조사 결과표, 비교 매트릭스, 질문 영역과 문항 구조표, 진단 항목표, 현행 절차 단계표
    + 도출 중심 Task는 분석 결과에서 시사점, 전략, 과제, 지표, 모델을 만듦. 채움본은 기준표나 산출물 시안 표
- 규모 수치는 셀 수 있는 업무에만 부여. 셀 수 없는 업무는 대상 기관명, 자료명, 판단 기준을 실명으로 특정
- 사전조사 표의 값은 실제 조사 결과로 채움(웹검색 불허 시 모델 지식). 확인하지 못한 셀은 `[확인]`. 표 아래 `※ 사전조사 결과 (착수 후 [기관명] 자료로 갱신)` 부기(웹검색 허용 여부와 무관하게 유지)
- `check density`는 (목적), 표 또는 그림, 산출물, 구체성 근거의 존재를 판정. 구체성 근거는 단위가 붙은 규모 수치(건, 명, 회, 개소, 개, 종, 차, 주, 일, 개월, 기관, 과제, 표본, 응답) 또는 대상, 자료, 방법, 기준, 절차, 범위, 규모, 구성, 설계, 산정, 선정, 편성, 기록 중 하나를 담은 괄호 소제목
    + Task 1개의 수치 표기가 6개를 넘으면 셀 수 없는 업무에 수치를 붙였는지 경고

### 논증 절 구성

- 특장점은 역량 주장 3-4개의 반복 구조. 주장마다 □ 판단문, ❍ 분야별 부연, 실명 과거 과업 하이픈, 실적 표 순으로 구성. 판단문의 문형 예시는 content-models.md
- 추진전략은 전략 3-4개. 전략마다 □ 판단문, ❍ 2-3개, 뒷받침 표 또는 그림 순으로 구성. 제안전략서 도출 표의 위험 요인마다 답하는 전략을 둠
    + 추진전략은 이 과업의 효과적 수행을 위해 제안사가 택한 방안. 성립 조건은 특화와 차별화(정의는 제안전략서 절). 심사위원은 그 방안의 과업 난점 적합성과 경쟁사 대비 차별성을 읽음
    + RFP와 제도가 요구하는 일, 주어진 제약의 준수, 완료 시점은 모든 입찰자의 제안서에 공통으로 있음. 이 내용은 과업 특성으로 둠. 의무를 달성하는 특화 방안과 의무 위에 더하는 방안을 전략으로 씀
    + ❍의 서술 대상은 수단을 택한 근거(과업 대상의 사실), 수단의 구현 방식(단계, 도구, 판정 기준, 참여 주체, 산출물), 확보하는 가치. 구현되는 수행 내용은 번호 참조 없이 과업명으로 서술
    + 가치 ❍는 해소된 위험이 과업과 결과물에서 드러나는 모습을 서술. 예시로 "답변마다 근거 문서와 쪽 번호가 붙어 담당자가 원문과 대조 가능". 완료 시점과 도달 상태를 선언하는 문장과 "(도달 상태)" 같은 설계 라벨은 쓰지 않음
    + 뒷받침 표는 방식의 견본. 예시로 단계별 수행표(단계, 도구, 활동, 산출물), 품질 지표표(단계, 지표, 산식, 목표 수준), 사용 장면 시나리오표(상황, 이용자, 처리 경로, 결과), 분과 구성표(분과, 대상 분야, 위원 구성, 검토 안건), 수행 절차표(단계, 시점, 참여 주체, 산출물), 진단 기준표. 견본 표 아래에 `※ 참고용 시안, 확정치 아님` 부기
    + 시점 판단은 근거와 방식에 담음. 발주처 일정(예산 심의, 기획 주기, 상급 기관 심의)은 근거 ❍의 사실로 씀. 방식은 그 일정과의 연동으로 서술. 예시로 근거 "「국가재정법」상 중앙관서의 예산요구서 제출 기한은 매년 5월 31일"과 방식 "예산 요구 일정에 맞춘 사업 근거 확보"
- 논증 절 셋은 장 배치와 무관하게 WHY, WHAT, HOW로 역할이 갈림. 배경 및 필요성은 WHY(발주처가 이 과업을 왜 지금 필요로 하는지). 특장점은 WHAT(제안사의 보유 자산. 방법론, 실적, 인력, 도구, 데이터). 추진전략은 HOW(이 과업의 난점을 어떤 원칙과 활동으로 넘을지. 결과물 설계 원칙, 수행 활동, 검증 방법)
    + 같은 방법론이 두 절에 나오면 특장점에는 보유 사실과 적용 실적 표를, 추진전략에는 이 과업에서의 적용 방식을 둠
    + WWH 프레임워크(WHY, WHAT, HOW)는 설계 언어(용어 절)
- 특장점은 00_제안전략서.md 차별화 포인트의 전개. 추진전략은 차별화 포인트와 추진전략 도출 표의 전개. 전략서에 없는 강점을 본문에서 새로 만들지 않음. content-models.md의 전략 예시 표는 문형 참고용

- 우선순위 산정표와 평가표는 재현 가능한 기준과 산식으로 제시

### 추진일정표

- 추진일정표는 기호 셀(`■`, `●`)로 기간과 시점을 표시한 표 1개. 첫 열 Module, 둘째 열 Task, 이후 열은 월(1M, 2M) 또는 주차
    + 기간 셀은 `■` 하나만 적으면 조판 시 회색 음영 셀로 전환. 보고회 행은 `●`로 시점을 표기
    + 기호 하나만 있는 셀(`■`, `●`)은 열 정렬 판정에서 글머리로 세지 않음. 월 열은 가운데 정렬로 조판. 첫 열의 같은 Module은 자동 세로 병합

### 장표 처리

- 한 쪽을 넘는 표는 장표 처리 대상. 표는 '글자처럼 취급' 속성으로 조판. 남은 쪽 공간보다 긴 표는 표 전체가 다음 쪽으로 밀림. 앞 쪽에는 빈 공간이 생김. 한 쪽보다 긴 표는 넘친 부분이 잘림. `build` 린트가 25행 초과 또는 추정 30줄 이상인 표를 `[장표 HITL]`로 알림
    + 기본 방식은 착수 질의의 유저 답변. build에 `--long-table`로 전달. 25행 이하인 긴 표는 기본 처리 대상에서 제외. 이 표는 같은 방식의 지시 줄을 캡션과 표 사이에 기입
    + 린트가 알린 표의 목록과 적용한 방식을 유저에게 보고. 표에 따라 다른 방식이 나아 보이면 그 표만 택일을 질의
    + `(장표: engine)`은 '글자처럼 취급' 속성을 해제. 한/글이 쪽 경계에서 표를 행 단위로 나눔(제목행 반복). `(장표: split N)`은 표를 N행 단위의 표 여러 개로 물리 분할(제목행 재부착, N 생략 시 12)
    + 해제 범위는 지시 줄을 붙인 표 1개. 다른 표와 밴드는 '글자처럼 취급'을 유지
    + `(장표: engine)` 표는 속성 해제로 표 앞뒤 문단과의 간격이 다른 표와 달라짐. 간격 유지가 필요한 표는 `(장표: split N)`을 택일안으로 제시
    + 분할 위치가 어색하면 원고에서 논리 단위(모듈, 분야, 연도)로 표를 나눔. 나눈 표의 캡션에는 (1), (2)를 붙임
    + 장표 지시를 붙인 표는 렌더링 PNG에서 분할 위치, 빈 공간, 하단 여백 침범, 머리글 서식 번짐을 검수
- `(장표: split N)`은 행 수 기준 분할. 행 높이와 셀 병합은 고려하지 않음. 이 제약으로 아래 경우에 결함이 발생
    + 셀마다 글머리가 여러 줄인 표는 조각 높이가 한 쪽을 넘음. 이 조각은 하단 여백과 쪽번호를 침범. 셀에 글머리가 2줄 이상 들어가는 표는 N을 6-8로 낮춤
    + 첫 열을 세로 병합(`^`)한 표는 분할 2쪽부터 머리글 서식이 본문 행에 번짐. 첫 열 병합 값도 유실. 이 표에는 split을 적용하지 않음
    + 첫 열 세로 병합 표의 처리는 논리 단위(Module, 분야, 연도) 분할과 캡션의 (1), (2) 표기. 대안은 세로 병합 해제와 각 행의 값 반복 기입
    + 모듈총괄표는 첫 열 세로 병합이 기본. 분할 기본값은 Module 단위
    + 논리 단위로 나눈 표 1개가 다시 한 쪽을 넘으면 그 단위를 Task 묶음으로 한 번 더 나눔. 나눈 표마다 첫 행에 첫 열 값을 기입. 25행 이하이면서 추정 30줄 미만인 표는 린트 알림 대상 밖. 이 표는 PNG로 확인
    + 열이 6개를 넘으면 행열 전환이나 표 분할을 유저에게 질의(추진일정표처럼 기호 셀로 채운 열은 열 수에서 제외)

## 독자 관점 서술

- 제안서의 독자는 심사위원과 발주처 담당자. 문장은 독자가 얻는 성과와 그 수단을 서술. 작성자의 사고 과정은 담지 않음
- 판정 원칙은 삭제 테스트. 문장을 지웠을 때 심사위원이 잃는 정보가 없으면 작성자나 문서를 향한 서술. 해당 문장은 삭제하거나 과업 내용으로 교체. 아래 유형 목록은 자주 나오는 형태. 목록에 없는 변형도 같은 원칙으로 판정
- 사고 과정의 노출은 "역산하여", "검토한 결과 판단하여", "이를 바탕으로 도출한", "배점을 고려하여 배치한"처럼 작성자가 어떻게 생각했는지를 적는 문장. 독자에게는 정보가 없음. 공급자 시각으로 읽힘
- 발주처가 얻는 내용의 서술 방식은 절의 성격에 따라 다름. 성과의 정의는 제안전략서 절
    + 배경 및 필요성과 절별 메시지는 발주처가 얻는 내용을 성과로 서술. 추진전략은 해소하는 위험과 확보하는 가치로 서술. 산출물은 그 성과와 가치에 이르는 수단으로 서술. 판단문별 종결 규칙은 스토리라인 확정 절
    + 수행부문(Module, Task)은 산출물 명칭을 실명으로 서술. 모듈과 Task의 목적은 methods.md 공통 표준의 모듈과 Task의 목적 절이 단일 원천. 목적은 산출물 및 활동이 결과물에 공급하는 내용으로 종결
    + 수행부문의 목적이 산출물의 내용과 활용처 없이 산출물 명칭의 나열로만 이어지면 보고서 납품으로 끝나는 제안으로 읽힘. 발주처의 성과는 논증 절과 절별 메시지의 내용. 모듈과 Task마다 되풀이하지 않음
- 판단 과정의 서술은 발주처가 얻는 내용으로 바꿔 씀. 그 자리에 배경은 성과를, 추진전략은 원칙과 해소하는 위험을, 수행부문은 산출물 및 활동과 그 활용처를 적음
    + (추진전략) "자료 특성을 고려하여 변환 방식을 설계" → "표와 그림까지 추출하는 문서 변환으로 HWP 보고서의 수치 누락을 방지"
    + (모듈과 Task의 목적) "현황을 조사하여 결과표를 작성" → "기관별 현황 조사로 개선 대상 선정의 근거를 확보"
    + "최종보고 시점에서 역산하여 조사를 편성" → "중간보고 시점까지 조사 결과표를 제출"
    + "RFP 요구항목을 검토하여 누락 없이 배치" → "세부 과업별 산출물과 제출 시점을 조견표로 제시"
    + "자료 확보 가능성을 판단하여 조사 대상을 선정" → "OO공단이 보유한 시설 대장, 점검 이력, 도면 목록과 공공 통계를 조사 대상으로 확정(착수 전 목록표 협의)"
- 방법의 서술도 독자가 확인할 수 있는 형태로 작성. 절차는 단계와 산출물로, 판단은 기준표로, 선정은 대상 목록으로 보임
- 문장의 중심 내용은 과업 이후에 일어나는 변화. 변화는 서술부에 대상과 상태로 기입. 주어를 바꾸는 방식으로 표현하지 않음
    + 개조식 문장은 주어 생략이 자연스러움. "상급 기관 심의의 보완 요구를 사전에 해소"는 주어 없이도 누가 무엇을 얻는지 읽힘
    + 시점은 발주처 일정의 사실(예산 심의, 기획 착수, 제도 시행)이 논지를 받칠 때 씀. 산출물의 완료 시점은 추진일정표와 산출물 제출 계획표에 둠
    + "발주처는 OO을 확보", "발주처가 OO을 달성"처럼 같은 주어가 되풀이되면 심사위원은 어느 기관에나 붙는 문장으로 읽음
- '발주처'의 사용 범위는 SKILL.md, 참조 파일, 설계 파일(00_제안전략서.md, 02_스토리라인.md 등). 원고에는 기관 실명을 사용(정의는 용어 절)
    + 독자는 자기 기관을 '발주처'로 부르지 않음. 원고가 독자를 '발주처'로 부르면 독자는 문장 속에서 제3자가 됨. 서술부를 성과로 채운 문장에서도 이 호칭은 공급자의 자리에서 쓴 글임을 드러냄
    + 실명으로 부르면 같은 문장이 그 기관의 사정을 다루는 글로 읽힘. 수요자 관점은 서술부의 내용과 호칭이 함께 갖춰질 때 완성됨
    + 호칭은 00_제안전략서.md 기관 호칭 절의 기관명을 사용. 약칭은 RFP나 기관 공문이 쓰는 표기만 사용
    + 실명도 필요한 자리에만 사용. 같은 □ 아래에서 실명이 되풀이되면 첫 자리 이후는 주어를 생략
    + 템플릿과 예시의 `[기관명]` 자리는 기관 호칭 절의 표기로 바꿔 씀. 회의체, 협의, 보안, 부기 문구도 같음. 예시로 "(발주처 협의)"는 "(OO공단 협의)", "※ 위원은 발주처와 협의하여 확정"은 "※ 위원은 OO공단과 협의하여 확정". 뒤따르는 조사는 실명의 받침에 맞춤. 채우지 않은 자리는 `check tone`이 FAIL로 색출
    + 추진체계도 등 그림의 상자 이름도 기관 실명으로 기입
    + 수행실적 표의 열 이름 "발주처", "발주기관"은 과거 과업의 계약 상대를 가리키는 관행 표기. 그대로 둠
- 아래 공급자 선언은 `check tone`이 FAIL로 색출. 문장 삭제 후 내용으로 진입
    + (숫자 선언) "3대 전략", "4개 Module", "5개 영역", "자료 6종". 항목 자체를 □, ❍, 목록표로 제시. 자기 구조와 자료의 개수는 선언하지 않음. 개수는 독자가 셈. 숫자 선언은 원고 후반으로 갈수록 늘어남. 모듈 개요표와 Task 서술에서 재확인. 외부 사실의 수량(23개 출연연, 시행계획 3건)은 출처로 확인한 값을 논지에 필요한 자리에만 사용
    + (RFP 대응 선언) "RFP 요구사항에 부합하도록", "제안요청서의 취지에 맞게", "과업지시서에 따라". 대응 여부는 Task 명칭과 서술에 그대로 쓴 요구항목 원문으로 보임
    + (본 과업 선언) "본 과업은", "본 과업 기간", "본 제안은", "본 연구에서는". 자기 지시 삭제 후 과업 내용으로 시작. 지칭이 필요하면 "과업" 또는 사업명 실명. 표 캡션과 셀에서도 같음
- `check tone`은 아래 공급자 서술도 FAIL로 색출
    + (전제 서술) "발주처의 자료 협조를 전제로", "OO가 확보되어야 수행 가능". 수행 위험을 발주처에 넘기는 문장으로 읽힘. 자료 확보 방법을 제안사의 절차로 서술. 발주처 협조사항은 RFP가 해당 절을 지정한 경우에만 관리부문에 표로 제시
    + (제외 선언) "본 과업 범위에 포함하지 않음", "OO은 다루지 않음". 발주처가 묻지 않은 제외 범위를 선언하지 않음. RFP가 명시한 제외만 과업 범위에 반영
    + (RFP 주어 서술) "RFP가 제시한 기능 구분", "RFP가 요구한 절차". RFP를 문장의 주어로 세우면 작성자가 문서를 읽고 있음이 독자에게 보임. 제시된 내용 자체를 서술("교통, 환경, 안전의 기능 구분과 대응"). RFP 문서 자체의 언급은 요구항목 조견표의 머리글에만 허용
    + (핵심 워딩과의 구분) 핵심 워딩(과업명, 세부 과업 명칭, 산출물 명칭, 발주처 용어)은 원문 표기 그대로 □, ❍, Task 명칭에 사용. `check wording`이 출현을 판정. RFP 주어 서술의 판정 대상은 "RFP에 따라", "RFP가 요구한"처럼 문서를 지시하는 문장
    + (표 지시 메타 서술) "아래 표는 OO을 보인 예시", "다음 표는 OO 계획". 표를 소개하는 문장은 삭제. 표 앞에는 표의 요지를 담은 ❍를 배치. "예시", "시안"임을 밝혀야 하면 표 아래 ※로 부기
    + (순서 열거 서술) "첫째 OO, 둘째 OO, 셋째 OO", "첫 번째는", "하나는 OO, 다른 하나는 OO", "마지막으로". 산문의 열거 표지는 개조식 계위와 중복. 항목마다 ❍ 1개를 둠. 순서는 계위가 보임. 항목이 4개 이상이면 표로 전환

## 자기완결 서술

- 절, □, Task는 각각 그 자리에서 읽혀야 함. 독자가 다른 쪽이나 원본 문헌을 찾아보게 만드는 서술은 결함
- 다른 절, 모듈, Task를 번호로 가리키지 않음. "Task 1-1의 정책 요건 목록을", "Module 2의 산출물은", "앞 절에서", "전술한 바와 같이"를 쓰지 않음. 필요한 내용을 그 자리에 다시 서술("정책 요건 목록의 항목을")
    + 번호 참조는 독자를 원본 위치로 보냄. 한 곳의 수정은 참조한 곳 전부의 수정을 부름. 원고의 분해와 재조립도 어려워짐
    + 번호 참조는 표 셀(모듈총괄표, 요구항목 조견표, 추진일정표, 업무분장표, 회의체 운영(안) 표)에만 허용. `check tone`이 본문 줄의 번호 참조를 FAIL로 색출(판정 명칭은 교차 참조)
- 단계 사이의 연계는 산출물 이름으로 서술. "현황조사에서 확보한 기관별 현황표는 개선 대상 선정의 후보 목록"처럼 앞 단계의 산출물 이름과 뒤 단계의 활용 방식을 한 문장에 담음
- 인용 자료는 그 자리에 결론 수치와 출처를 적음. "별첨 참조", "원문 참조"로 미루지 않음
- 소프트웨어 설계 어투는 시스템 아키텍처를 설명하는 자리에만 씀. "입력이 되고", "입력 자료로 사용", "출력", "연결을 확보", "연계 구조", "매핑", "인터페이스"가 해당. 정보화 과업의 수행계획에서도 Task의 산출물을 다른 Task의 입력으로 서술하지 않음. "활용 자료", "OO에 활용", "대응표"로 서술
- 자료와 사람의 의견을 기계 처리처럼 적지 않음. "면담 결과를 입력하여 도출" → "면담에서 확인한 의견을 과제 후보의 실행 가능성 판단에 반영"처럼 누가 무엇을 어디에 반영하는지로 서술
- 골격 언어와 내부 판단을 원고에 적지 않음. "과업의 답", "과업 방향", "전제조건", "수행 여건", "일정 정합", "근거 누적", "누락 없이 대응", "빠짐없이 배치", "대응 관계", "도달 상태", "도달 시점"은 작성자의 점검 언어. 독자에게는 결과만 제시. 배경의 마지막 단(A)은 "과업 방향" 라벨 없이 과업이 무엇을 하는지를 □ 판단문으로 직접 씀
- 설계 언어(정의는 용어 절)를 원고에 적지 않음. "분석형, 조사형, 도출형, 지원형 Task", "Task 배치", "수행내용 구성", "(2주 단위, 열 번호는 주차)" 같은 설명은 스킬의 작동 방식. 독자에게는 정보가 없음. 표의 구성 방식은 표에서 확인됨

## 문장 규율

- 한 문장에 메시지 1개. 주어와 서술이 하나의 관계만 가지는 단문
- 계위 1개에 문장 1개. 마침표로 두 문장을 한 줄에 잇지 않음. 뒤 문장은 하이픈 계위나 다음 ❍로 분리. 줄 끝에 마침표를 붙이지 않음. `check tone`이 □, ❍, 하이픈, ※ 줄의 줄 안 마침표와 줄 끝 마침표를 FAIL로 색출 (표 셀, 각주, 출처 줄, 캡션은 제외)
    + ※ 부기에 두 사실을 담을 때는 괄호로 묶음. 예시로 "※ 사전조사 결과 (착수 후 OO공단 자료로 갱신)"
- 5W1H 단문. 한 문장에 누가, 무엇을, 언제, 어디서, 왜, 어떻게의 요소를 각각 최대 1개만 담음. 요소가 2개 이상 겹치면 문장을 나눔
    + 예시로 "제안사는 의사결정 속도를 높이기 위해 착수 2주 내에 OO공단 보유 자료 목록을 확정" (누가, 왜, 언제, 무엇을 각 1개)
    + 복문 예시로 "자료를 확보하고 대상을 선정하여 조사를 수행" → 3문장 또는 하이픈 3개로 분리
- 비문을 쓰지 않음. 주어와 서술의 호응("제안사는 OO을 확보"로 씀. "제안사는 OO이 확보"는 비문), 목적어 누락("OO을 분석"에서 무엇을), 명사형 종결과 앞 조사의 불일치("OO에 대해 검토"는 "OO을 검토"로 씀)를 점검. 원고를 소리 내어 읽었을 때 걸리면 비문
- 명사형 종결(-함, -임, -필요, -추진, -제시). 존댓말과 구어체를 쓰지 않음. 부자연스러운 종결은 lexicon.md 종결 어휘 절 참조
- 제안서는 격식 문어체. 전문적으로 보이는 구어체는 격식체로 착각하기 쉬움. 다음 표지는 `check tone`이 FAIL로 색출
    + (추측과 완곡 종결) -듯, -듯함, -인 셈, -하는 편, -할 만함, -로 봄, -로 보임, -로 여겨짐. 판정을 흐리는 표지. 근거와 함께 "-로 판단", "-로 확인", "-로 집계"로 종결. 의존명사는 띄어 쓴 형태만 색출. "개편", "재편", "데이터", "센터" 종결은 판정에서 제외
    + (설명체 어미) -는데, -인데, -더라, -거든, -잖아. 문장 분리 후 명사형으로 종결
    + (구어 축약) -하는 게, -할 거, -한 걸, -하는 건. "것이", "것을"의 축약. 명사형으로 전환
    + (구어 관형과 부사) -식으로, -쪽으로, 일단, 약간, 좀, 꽤, 딱, 그냥, 나름. 삭제하거나 수치와 기준으로 대체
- 구어체 형태의 "것" 종결을 쓰지 않음. "남은 것", "해야 할 것", "과업의 포인트인 것", "OO것임"은 커뮤니티 구어체의 종결. `check tone`이 FAIL로 색출. 명사형 종결로 전환("OO 잔존", "OO 필요", "OO이 과업의 핵심"). 판정 대상은 줄 끝의 "것" 종결
- 연결어미(-으며, -하며, -이며, -하고)와 접속부사(그리고, 그러나, 그래서)로 술어 2개를 잇지 않음. 문장은 분리. 문장 간 관계는 계위로 표현
- 쉼표는 같은 범주 3개 이상 나열에만 사용. 2개 나열은 "A 및 B"로 표기. "및"은 발주처 공문의 관행 표기
- em dash, 물결표, 구분기호(/, ·, →), 연결 하이픈을 쓰지 않음(범위 표기의 하이픈은 허용). 표 셀 안의 개행은 `<br>`
- 대비 구문("X가 아닌 Y", "단순한 X를 넘어 Y")을 쓰지 않음. Y를 직접 서술
- 숫자 선언은 독자 관점 서술 절의 판정을 적용
- 글 자체나 작성 과정을 서술하는 문장을 쓰지 않음. "본 제안서는", "앞서 언급한", "정리하면"은 삭제. 문장은 내용으로 시작
- 사고 프레임워크명(MECE, 피라미드, 제1원칙, SCQA, SCR, WWH)과 스킬 작동 어휘(배점 역산, 밀도, 섹션대장)를 본문에 노출하지 않음. "역산"은 일정 문맥에서도 계산 과정의 노출. 쓰지 않음. 일정은 "체계적 일정 수립", "효율적 일정 편성"처럼 결과와 성격으로 서술. Module과 Task 명칭은 과업 설계의 실체. 원고에 표기
- 어휘는 references/lexicon.md의 기능별 관행 어휘를 사용. 금칙어의 우회 표현으로 구어나 비유 어휘("쓰임새", "얼개", "손질")를 만들지 않음. `check tone`이 색출하면 대체표로 교체
- 관리 외래어(작업분해도, 마일스톤, 임계경로)와 소프트웨어 설계 어투("입력값", "인계")를 쓰지 않음. 준구어 어휘(포인트, 세팅, 케이스, 니즈, 픽스, 체크, 컨펌, 어필, 메리트)는 lexicon.md 대체표의 격식어로 교체
- 격식은 어휘와 종결로 확보. 어려운 한자어를 쌓아 격식을 흉내 내지 않음. 어휘 수준은 발주처 공문과 상위계획의 어휘

- 자기 입찰 사업의 예산액을 본문에 기재하지 않음. 확인되지 않은 수치는 `[확인]` 또는 조사 과업으로 전환
- 비율과 합계는 코드로 재계산. 분자와 분모의 기준 시점이 다른 비율은 사용하지 않음

### 심층 검토

- 코드가 잡지 못하는 결함은 심사위원 관점의 검토로 발견. 심층 검토는 실행 환경과 무관하게 수행하는 5단계의 기본 절차. 검토 강도는 섹션의 통제배점으로 결정

| 통제배점 | 자체 검토 (기본) | 독립 검토 (유저 승인 시) |
|---|---|---|
| 10점 이상 | 1회 | 반복. 잔여 결함 없음에 도달하거나 3회 |
| 5점 이상 10점 미만 | 1회 | 1회 |
| 5점 미만 | 1회 | 미수행 |

- 자체 검토는 같은 세션에서 모델이 직접 수행. 서브에이전트나 새 세션이 없는 환경에서도 생략하지 않음. 파일에서 다시 읽은 원고를 아래 검토 항목과 하나씩 대조
- 독립 검토(새 세션, 별도 지시문, 서브에이전트)는 수행 가능한 환경에서만 유저 질의 후 수행. 질의는 자체 검토 결과 보고와 같은 턴에 묶음
    + (장점) 작성 과정을 모르는 검토자는 작성자가 반복해서 놓치는 결함을 발견
    + (단점) 검토자는 제안전략과 유저 확정 사항을 모름. 이로 인한 오판 지적이 나올 수 있음. 시간과 토큰 소모도 증가
    + 승인 시 검토자에게 00_제안전략서.md, 02_스토리라인.md, 검토 항목을 함께 전달
- 한 회차의 지적은 영향이 큰 5건까지로 제한. 지적을 늘리면 수정이 새 결함을 만듦
- 코드가 이미 처리한 항목을 재지적하지 않음. 검토자의 지적이 오판이면 근거와 함께 기각
- 검토 항목은 코드 점검이 판정하지 못하는 결함 유형으로 구성
    + (수치 무결성) 비율의 분자와 분모가 같은 기준 시점인지 확인. 같은 사실을 가리키는 수치가 두 값으로 존재하는지 확인
    + (출처 신뢰도) 인용 수치마다 별첨으로 제출 가능한 자료인지 확인. 유료 리포트와 출처 미상 보도치는 공공 통계로 교체
    + (논리 비약) 자료에서 결론으로 가는 중간 단계가 있는지 확인. 조건이 다른 두 사실을 등치했는지 확인
    + (이면 니즈 대응) 제안전략서의 이면 니즈 가설에 답하는 Task가 있는지 확인
    + (변별력) 경쟁사가 같은 문장을 쓸 수 있는지 확인. 제안사만 쓸 수 있는 근거(실적, 데이터, 인력)가 붙어 있는지 확인
    + (절 경계) 각 절의 □가 그 절의 역할(배경은 WHY, 특장점은 WHAT, 추진전략은 HOW)로 읽히는지 확인. 다른 절의 역할로 읽히는 □는 해당 절로 이동
    + (전략의 짝) 추진전략 □마다 도출 표의 위험 요인 1개와 확보하는 가치 1개가 읽히는지 확인. 활동 이름만 있거나 범용 운영 수단으로 읽히는 □는 원칙이나 활동의 설계와 위험으로 다시 작성. RFP 과업 내용과 제도 의무를 지우면 남는 방안이 없는 □는 특화 방안으로 다시 작성
    + (독자 관점) 문장이 작성자의 사고 과정이나 작업 절차를 말하는지 확인. 그러한 문장은 독자가 얻는 성과의 서술로 전환. 논증 절이 산출물의 제출로 끝나는지, 모듈과 Task의 목적에 산출물 및 활동의 결과와 활용처가 빠졌는지도 확인
    + (괄호 소제목) 논증 묶음에 붙은 괄호 소제목, 본문 낱말을 되풀이하는 괄호 소제목, 일부 항목에만 붙은 나열 묶음이 있는지 확인. 기준은 괄호 소제목 절
- 원고의 결함 수정 후 `check all` 재실행. 문체 일괄 수정 후에도 재실행

## 원본 이미지 재사용

- 제출 원본(RFP, 발주처 공개 자료, 유저가 제출한 pdf, hwpx, pptx, docx)이 있으면 `extract_images.py`로 삽입 후보를 추출. 산출은 img_NNNN.png와 manifest.json(크기, 비율, 유형 photo, logo, map, diagram, 출처 쪽)
- 채택 대상은 발주처 사업 개념도와 추진체계도, 유사 실적의 현장 사진과 결과물 화면, 차트, 구조도와 아키텍처 도식, 지도, 회사와 기관 로고. 본문형 문서에서 원본 차트와 구조도의 삽입은 일반적인 관행
- 미채택 대상은 표를 캡처한 이미지(표로 재구성), 불릿과 배경 조각, 해상도가 낮아 인쇄 시 깨지는 이미지, 다른 제안사의 도식
- 삽입은 유저 확인 후에만 수행. 모델은 manifest와 원본 쪽을 근거로 후보 목록(파일, 출처 쪽, 유형, 삽입 위치, 캡션안)을 제시. 원고에는 유저가 채택한 항목만 배치
- 삽입은 원고에 `![캡션](경로)`. 외부에서 가져온 그림은 다음 줄에 `※ 출처: 기관명(연도), 자료명`. 크기, 배치, 캡션은 조판기 그림 규칙(가로형 폭 140mm, 정사각형 근방 폭 90mm, 세로형 높이 110mm, 투명 표 안 가운데 배치, 출처는 그림 아래, 캡션은 투명 표 아래)이 그대로 적용됨
- 상대 경로는 build가 만드는 납품/_합본.md 위치 기준으로 풀림. 작업폴더의 그림은 원고/와 납품/에서 같은 파일을 가리키는 상대 경로(예시로 `../그림/파일.png`)나 절대경로로 기입
- build 로그에 `WARN: 이미지 없음`이 나오면 그 그림과 캡션은 납품본에서 빠짐. 경로 수정 후 재조판
- RFP 본문의 그림을 그대로 쓸 때도 출처를 표기. 원본 이미지의 저작권과 사용 권한은 제안사가 확인
- 발표자료의 도식(도형과 글상자로 그린 절차도, 체계도)은 내장 이미지로 추출되지 않음. `figure` 명령으로 기준본 PDF의 해당 영역을 캡처. 유저 확인 규칙은 같음. 절차는 deck-conversion.md 도식 캡처 절
- 후보가 많으면 `--min-px`, `--min-kb`로 하한을 올림. 로고는 작게 삽입됨. 로고 추출의 하한은 낮게 둠. 로고 후보는 logo 유형에서 선별

## 조판

- 기본 스켈레톤(작업폴더/_양식/proposal.hwpx)은 스타일만 정의한 빈 양식. 표 폭, 열 정렬, 머리글 배경, 단위 행과 출처 행, 캡션 부착, 그림 배치, 세로 병합은 조판기(scripts/hwpx_report.py)의 규범을 그대로 따름
    + 원천은 proposal.py 설정부의 SKELETON_* 정의와 python-hwpx의 빈 새 문서. init과 build가 실행마다 같은 내용으로 다시 생성
    + 양식 변경은 설정부 수정이나 `build --skeleton` 지정으로 수행. _양식 파일의 직접 수정은 다음 build에서 덮어써짐
    + 서체는 나눔바른고딕 단일 계열. 계위 간 중요도 차이는 글자 크기와 굵기로 표현
    + 색은 밴드에만 적용. 테마는 navy(기본)와 mono(검정과 회색) 중 착수 질의 답변으로 선택. 색 값은 proposal.py 설정부 `THEMES`
    + 표 서식은 테마와 무관하게 검정 0.15mm 괘선과 회색(#D9D9D9) 머리글. 일정표 기간 칸도 같은 회색. 사유는 한/글에서 표를 고치는 편집자의 관행 서식 유지
    + 계위 기호는 □, ○, 하이픈, ·, ※. 근거는 「행정업무의 운영 및 혁신에 관한 규정 시행규칙」 제2조가 항목 표시에 허용하는 특수기호(□, ○, -, ·). 표 셀 글머리는 ·
- docx는 hwpx와 같은 원고, 같은 설정부 정의, 같은 조판 판단으로 생성
    + 스타일 수치(글꼴, 크기, 굵기, 정렬, 여백, 줄 간격), 계위 기호, 밴드, 표(열 폭, 괘선, 머리글 채움, 병합, 셀 여백), 캡션, 그림, 각주, 머리말, 쪽번호, 목차가 hwpx와 같음
    + 계위 기호는 Word 글머리 기능으로 표시. 줄 간격은 한/글 퍼센트 값을 고정 간격으로 옮김. 빈칸 폭은 한/글 기준(글자 크기의 절반)에 맞춤
    + 두 형식을 함께 산출하면 build가 문단 글자 순서를 대조. `WARN: hwpx와 docx 문단 글자 불일치`는 조판 코드 결함 신호. 유저에게 보고. 원고 수정으로 WARN을 없애는 처리는 결함
    + 한/글과 Word는 줄바꿈과 쪽 나눔의 계산 방식이 달라 줄 끝 위치와 쪽 경계가 일부 다름. 목차 쪽번호는 형식마다 자기 렌더링으로 산정
- 표 폭은 조판기 규칙으로 표마다 산정. 상한은 본문 폭에서 계위 들여쓰기를 제외한 값, 하한은 상한의 50%
    + 모든 열이 한 줄에 들어가면 열마다 한 줄 폭을 씀. 표가 하한보다 좁으면 비례 확대
    + 한 줄에 들어가지 않으면 표 폭을 상한으로 둠. 짧은 열은 한 줄 폭을 먼저 받음. 긴 열은 남은 폭을 고르게 나눔
    + 어절이 잘리지 않는 폭은 모든 열에 보장
- 같은 양식이 반복되는 표의 폭 통일은 모델이 원고에서 지정. 같은 양식 여부는 문서 설계의 판단
    + 지시 줄은 캡션과 표 사이에 둠. `(폭: 실적)`처럼 그룹명을 주면 같은 그룹의 표가 그룹 안 최대 필요폭으로 통일. `(폭: 1,3,2)`는 상한을 비율로 배분. `(폭: 1,3,2, 80%)`는 상한의 80%를 비율로 배분
    + 통일 대상의 통상 예시는 모듈 개요표(전 모듈), 연구책임자와 참여인력의 실적 표, 회의체 운영(안) 표, 조사 대상 목록표
    + `build --unify auto`는 머리글이나 첫 열 라벨이 같은 표를 자동으로 묶는 보조 수단. 기본값은 manual
    + 폭을 지정한 표는 렌더링 PNG에서 전부 확인. 확인 대상은 눌린 열, 큰 빈 폭, 그룹 안 표끼리의 부조화. 결함이 보이면 지시 제거 또는 비율 값 변경 후 재조판(지시를 제거한 표는 표마다 산정으로 복귀)
- 제안서 고유 요소는 로마자 장 번호, 아라비아 절 번호, 가나다 항, 밴드(장, Module, Task), 표 폭 지시
    + 밴드는 번호 칸, 빈 칸, 제목 칸의 1행 표. 밴드 간 중요도 차이는 번호 칸의 무게로 표현. 장은 짙은 색 채움 칸의 흰 로마자, Module은 옅은 색 채움 칸의 짙은 색 라벨, Task는 짙은 색 테두리 칸의 짙은 색 라벨
    + 제목 글자는 장 20pt, Module 13.5pt, Task 12pt 굵게. Module과 Task의 번호 칸은 같은 폭. 두 밴드의 제목 시작선이 맞음
    + 캡션은 기본 무번호. 표는 <제목>, 그림은 [제목]. 밴드 표는 번호 집계에서 제외(numberingType NONE). 자동번호를 켜면 장마다 1부터 재시작
    + 밴드 앞뒤 여백과 다음 문단 붙임은 밴드 위치 스타일이 담당. 칸 폭, 색, 글자 크기, 높이는 proposal.py 설정부 `BAND_STYLE`
- 간지는 장마다 본문 앞에 들어가는 쪽. 장 번호와 장 제목을 큰 장 밴드로 쪽 가운데보다 약간 위에 배치. 본문은 다음 쪽의 첫 절부터 시작
    + 간지 쪽에는 머리말, 꼬리말, 쪽번호를 표시하지 않음. 쪽 수 집계에는 포함
    + hwpx는 한/글의 감추기 기능, docx는 구역의 첫 쪽 구분으로 같은 결과를 만듦
    + 밴드 크기와 위치는 proposal.py 설정부 `BAND_STYLE["divider"]`와 `DIVIDER_TOP_LINES`
- 납품 hwpx와 docx는 나눔바른고딕 보통과 굵게를 씀. 두 굵기는 KS X 1001 한자를 포함. 글꼴이 없는 PC의 한/글과 Word는 대체 글꼴로 표시하여 줄 끝과 쪽 경계가 달라짐
- 글꼴 설치 안내는 첫 납품의 최종 보고에 아래 항목으로 기재. 유저가 설치를 마쳤다고 알린 뒤에는 생략
    + (설치 원천) 네이버 한글 배포 사이트(hangeul.naver.com)의 나눔글꼴. 필수 글꼴은 나눔바른고딕 보통과 굵게
    + (설치 방법) Windows는 글꼴 파일의 오른쪽 클릭 메뉴에서 모든 사용자용으로 설치. macOS는 글꼴 파일을 열어 서체 관리자로 설치
    + (적용 확인) 한/글과 Word를 모두 닫고 다시 실행. 납품 파일 본문의 글꼴 이름이 나눔바른고딕으로 표시되면 완료
    + (외부 전달) 받는 쪽 PC의 글꼴 설치 여부를 알 수 없으면 한/글 또는 Word에서 저장한 PDF를 함께 전달
- build의 `--toc`(목차)와 `--page-number`(쪽번호)는 서로 다른 옵션. 둘 다 기본 OFF. 사전진단보고서의 기본값은 references/report.md 조판 절
    + 유저가 요청했거나 RFP 작성 규정이 명시 요구한 경우에만 켬. 켜는 근거(착수 질의 답변 또는 RFP 작성 규정)는 00_제안전략서.md 사업 기본조건의 작성 규정 행에 기록. 사전진단보고서는 00_진단서.md, 기획보고서는 00_기획설계.md의 기본 정보 표에 기록
    + RFP가 쪽번호만 요구한 경우 `--page-number`만 켬
    + `--toc`를 켠 경우 렌더링 후 목차의 쪽번호 기입 건수를 전수 확인. 근사 렌더러가 장 제목 일부를 찾지 못하면 쪽번호가 빈 칸으로 남음. 쪽번호 기입은 `--page-number`를 함께 켠 경우에만 수행. build 로그의 `목차 쪽번호 n/m건 기입`과 목차 쪽 PNG를 함께 대조
    + 제안서는 누락이 1건이라도 있으면 목차 해제 후 재조판. 목차 유지가 필요하면 한/글의 목차 갱신 필요 문구를 최종 보고에 기재. 사전진단보고서와 기획보고서의 처리는 report.md 조판 절
- 발주처 양식은 `skeleton 양식.hwpx 스켈레톤.hwpx`로 추출. 프로파일 초안의 null 역할에 스타일명 기입 후 `build --profile 프로파일.json --skeleton 스켈레톤.hwpx` 실행

### 문서 라벨

- 문서에 찍히는 고정 문자열, 원고 표기, docx 언어 태그, 납품 파일명은 라벨. 기본 라벨은 한국어 문서를 만듦(목  차, 표 목차, <표 1-1>, [그림 1-1], 가., 제1장, 납품/제안서)
- 다른 언어 문서는 라벨 파일(JSON)을 `build --labels 파일` 또는 `check --labels 파일`로 지정. 작업폴더의 지정 경로는 state.json에 기록되어 이후 check와 build가 같은 라벨을 씀. `--labels none`은 기록 해제
- 바꿀 수 있는 키 묶음은 formats(제목 번호 서식), letters(가나다 계위), toc(목차 제목), caption(캡션 낱말과 괄호, docx 번호 필드), notation(원고 표기 추가), language(docx 언어 태그), output(납품 파일명). 키 표, 기본값, 영어 예시는 references/labels.md
- 일부 키만 적어도 됨. 빠진 키는 기본값. 모르는 키와 형식 오류는 build와 check가 ERROR로 중단
- notation은 표기를 추가만 함. `출처:`, `<표>`, `(단위: )` 같은 한국어 기본 표기는 계속 인식
- 로마자 장 번호와 계위 기호는 언어와 무관하여 라벨 대상이 아님
- docx 기본 언어 태그는 라틴 en-US, 동아시아 ko-KR. 라틴을 ko-KR로 두면 LibreOffice가 영문 낱말과 숫자 중간에서 줄을 바꿈
- 한국어가 아닌 원고는 한국어 전용 점검을 `check all --skip`으로 생략(점검 절)

## 렌더링 검수

- 렌더링 후 페이지 PNG 전부에서 아래 항목을 검수
    + 계위 기호와 들여쓰기 단차, 밴드의 위치와 밴드 앞뒤 간격
    + 표의 가운데 배치, 열 정렬 일관성, 머리글 배경, 캡션 위치, 단위 행 위치, 출처 행 위치, 라벨 열 병합의 적정성
    + 그림 크기와 캡션, 텍스트 잘림과 겹침
    + 표와 그림의 앞뒤 간격. 표나 그림의 아래 테두리에 다음 번호 제목(장 밴드, 절 1., 항 가., 목 1)), Module과 Task 밴드, □, ❍가 붙어 있거나 위 문단과 겹치면 결함. 다른 표의 앞뒤 간격과 같은 폭이 확보되었는지 표마다 확인
    + 간격 결함은 `(장표: engine)` 표의 뒤에서 주로 발생. 발견 시 해당 표의 지시 줄을 `(장표: split N)`으로 교체 후 재조판. 이후 PNG를 다시 확인
    + 쪽 경계에서 표와 캡션의 분리, 한 쪽을 넘는 표의 분할 위치와 제목행 반복, 절 시작 직후의 빈 쪽, 쪽 끝에 홀로 남은 밴드와 제목과 □
- 항목 검수 뒤 목록 없이 자유 검수 1회. 계위 간 좌측 정렬선, 표 폭과 본문 폭의 균형, 여백의 일관성, 한 쪽 안의 시각적 무게, 계위별 글자 크기와 굵기의 차이를 함께 봄
- 원인이 원고면 원고를 수정. 원인이 규범이면 proposal.py 설정부를 수정. 같은 성격의 결함 3건 이상이면 개별 교정 중단 후 proposal.py 설정부에서 규범을 조정

### 규칙 밖 결함의 재량 조정

- 검수 항목은 자주 나오는 결함만 수록. 규칙 밖의 지점도 처음 받은 실무자가 이상하게 보면 결함으로 조치
- 규칙대로 조판한 렌더링 결과가 보기 나쁘면 보기 좋은 쪽을 선택
- 읽기에 이상한 문장은 문장 규율 밖의 사항이라도 고침. 판단 기준은 심사위원이 읽다가 멈추는지 여부
- 조정 수단은 원고 수정, 표와 그림의 형태 교체, □ 분할과 병합, 설정부 상수 조정. 조정은 같은 계위 전체에 적용
- 재량으로 바꾼 사항은 무엇을 왜 바꿨는지 최종 보고에 1줄로 기재
- rhwp와 H2Orestart는 근사 렌더러. `render`는 검수 사본에만 표시 보정을 적용. 표 셀 글머리(·, -)의 글자 삽입은 soffice 경로에만 적용(rhwp는 셀 글머리를 직접 그림. H2Orestart는 그리지 않음). 두 경로 모두 검수 PNG에 글머리가 1개씩 보이는 상태가 정상. 납품 hwpx는 무변경(한/글은 스타일 글머리로 표시)
    + 자동번호 캡션 사용 시 번호 미표시(`<표 1- >`), 구역별 쪽번호, 글꼴 대체, `(장표: engine)` 표의 제목행 반복 표시는 판정 대상에서 제외
    + rhwp의 알려진 근사 표시도 판정 대상에서 제외. 나눔 글꼴 영문의 좁은 표시, ※ 뒤 간격 소실, 각주 구분선과 본문의 겹침, 어절 중간 줄바꿈, 다음 문단과 함께 설정의 미반영(쪽 끝에 홀로 남은 제목과 □), 쪽번호를 켰을 때 본문 마지막 줄과 쪽번호의 겹침, `(장표: engine)` 표의 하단 여백 침범이 해당
    + rhwp에서만 보이는 배치 결함은 `render --engine soffice --outdir 폴더`로 교차 확인. `--outdir`는 rhwp 산출 PDF를 보존. soffice에서 정상이면 근사 표시로 판정. 근사 표시는 원고 수정 대상에서 제외(수동 쪽 나눔은 한/글의 실제 배치를 바꿈)
    + H2Orestart의 알려진 근사 표시도 판정 대상에서 제외. 캡션 미표시와 셀 안쪽 여백 무시가 해당
    + LibreOffice의 docx 표시 차이도 판정 대상에서 제외. 한글과 숫자 사이의 자동 간격(docx의 자동 간격 해제 설정을 읽지 않음), 쪽 경계에서 나뉜 표의 제목행 미반복이 해당
    + 최종 확정은 유저의 한/글 확인(docx는 Word 확인). 최종 보고에 1줄 고지

### PDF 동봉

- 동봉 여부는 착수 질의 답변으로 정함. 기본은 미동봉
- 검수 PDF와 PNG는 `render --outdir`로 납품 폴더 밖에 산출. 교차 확인의 렌더링은 다른 폴더에 산출
- 동봉을 고른 경우 형식마다 마지막 render의 PDF를 납품 폴더에 복사하여 hwpx 또는 docx와 함께 전달
- (근사 렌더링 안내) 착수 질의와 PDF를 동봉한 최종 보고에 아래 내용을 제시
    + PDF는 근사 렌더러가 그린 파일이므로 한/글과 Word의 표시와 다를 수 있음
    + hwpx의 PDF는 줄바꿈, 간격, 쪽 경계의 표시 결함이 포함될 가능성이 높음
    + 제출용 PDF는 한/글 또는 Word에서 저장

- (의무 재진술형 추진전략) "요구 산출물의 충실한 작성", "부처 대응일정 준수", "보안 규정 준수", "국가 망 보안체계 기반 설계"처럼 RFP와 제도가 이미 요구하는 일이 전략의 내용. 모든 입찰자가 같은 문장을 쓸 수 있음. 그 의무를 어떤 특화 방식으로 달성하는지를 판단문으로 작성. 예시로 "자료 등급별 처리 경로 분리로 국가 망 보안체계 안에서 생성형AI를 활용"
- (공급자 시점의 스토리라인) 추진전략 판단문과 절별 메시지가 제안사의 작업 방식으로 끝남. 유저가 승인 단계에서 같은 교정을 반복하게 됨. 제시 전에 절별 메시지의 종결은 발주처가 얻는 성과로, 추진전략 판단문의 종결은 해소하는 위험이나 확보하는 가치로 옮김
- (추상 호칭의 반복) 수요자 관점을 주어 교체로 구현한 결과 "발주처는", "발주처가"가 원고 전반에 되풀이됨(사유는 독자 관점 서술 절). 주어 삭제 후 서술부에 대상과 상태를 기입. 호칭이 필요한 자리는 기관 실명으로 작성
- (산출물로 끝나는 성과) 발주처가 얻는 내용을 보고서와 결과표의 제출로 서술. 보고서 납품으로 끝나는 제안으로 읽힘. 산출물 이후에 발주처에게 일어나는 변화로 다시 작성
- (회의체 명칭 나열) 구성, 회차, 안건, 활용처가 없음. 운영(안) 표로 특정
- (도출 중심 Task의 분석 중심 서술) 기준과 수행 절차 없이 분석 대상과 규모만 기재. 기준표 배치
- (모듈 도입부 생략) Module 밴드에서 Task로 직행. 모듈마다 (목적), (추진방안), 개요표 배치
- (Task 안의 단계 혼재) Task 밴드 아래에 밴드명을 되풀이하는 □를 두거나 라벨 ❍ 사이에 라벨 없는 결론 ❍를 둠. 밴드 아래에는 라벨 ❍만 둠. 결론은 해당 라벨 아래 하이픈으로 내림
- (금칙어의 직역 우회) "게이트"를 "관문"으로, "활용"을 "쓰임새"로 치환. lexicon.md의 관행 어휘 사용
- (표준 골격의 기계적 이식) 전략기획 골격을 RFP 과업 구조보다 우선 적용. RFP 과업 세부내용이 항상 우선
- (규모 불비례 기획) 수억 규모 사업에 대규모 재정사업급 분석 절차 제시. 분석 절차는 사업 규모에 비례하여 편성
- (폐지 제도의 현행 서술) 국가연구개발사업 예비타당성조사처럼 개편된 제도를 현행처럼 서술. 착수 시 현행 여부 확인
- (문서 목차 페이지 생성) 표지와 목차를 원고에 직접 생성. build 옵션 `--cover`와 `--toc` 또는 한/글에서 삽입(`--toc`를 켜는 조건은 조판 절)
- (장표 방식 임의 결정) 유저 질의 없이 engine이나 split을 임의로 정한 조판. 착수 질의 답변을 `--long-table`과 지시 줄에 적용
- (응답 전재) 원고를 대화 응답에 출력. 파일로만 산출
- (조판기 우회) python-hwpx나 python-docx API 직접 호출로 문서를 새로 조립. 스크립트 오류는 proposal.py 설정부나 원고에서 해결(API 변경에 따른 호출부 수정은 준비 절)
- (그림 생성) 도식과 차트를 코드로 그린 그림의 삽입. 범위 밖. 표로 재구성하거나 원본 이미지에서 채택
