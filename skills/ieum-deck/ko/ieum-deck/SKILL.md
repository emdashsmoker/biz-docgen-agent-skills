# ieum-deck

- (ieum-deck) 기획 논리를 한 줄 스토리라인으로 이어 편집 가능한 PPTX 로 조판하는 발표자료 스킬 (ieum 은 한국어 "이음")
- (목적) 사용자가 기획 논리와 내용 검토에 집중하도록 발표자료의 구성 설계와 조판을 대신 수행
- (목표) RFP, 원고, 자료를 바탕으로 lint, 구조 검수, 시각 검수를 통과한 편집 가능한 발표자료 초안을 산출
- (범위) 공공 용역 제안 발표자료와 보고회 발표자료를 중심으로 민간 기획서, 사내 보고, 교육 자료까지 적용
- 산출물은 사후 편집이 가능한 네이티브 PPTX (도형, 텍스트 상자, 표, 차트, 이미지)
- 모델은 슬라이드 내용을 `storyboard.json` 에 기록
- `scripts/build.js` 는 같은 storyboard 에서 항상 같은 PPTX 를 조판
- 디자인 수치는 `scripts/tokens.js` 한 곳에서 관리

## 이용 안내

- 스킬을 처음 실행한 작업에서는 착수 질의 직전에 안내 문구를 사용자에게 1회 제시
- 안내 문구는 요약이나 생략 없이 원문 그대로 제시
- 제시 여부는 `state.json` 의 `noticeShown` 에 기록하여 같은 작업을 재개할 때 반복 제시를 생략

### 안내 문구

- (실행 환경) 대용량 문서와 다단계 작업을 처리하므로 모델 등급과 토큰 한도가 산출물 품질에 영향
    + 의도한 품질을 얻기 위해 각 모델 제공사의 최상위 모델 사용 권장
    + 발표자료 1건에 많은 토큰이 소요되므로 착수 전 요금제 한도나 API 비용 확인 권장
- (산출물의 성격) 산출물은 제출 전 검토가 필요한 초안
    + AI 모델이 작성한 사실관계, 수치, 논리에는 오류가 포함될 수 있음
    + 제출 전에 사용자가 모든 슬라이드를 직접 검토하여 최종 수정
    + 기획 판단과 최종 결정은 사용자가 수행 (스킬은 작성과 조판을 보조)
- (수록 정보의 한계) 스킬에 수록한 제도, 평가 관행, 방법론 정보는 작성 시점의 해석이므로 현행 기준과 다를 수 있음
    + 현행 제도와 발주기관 기준은 착수 시 소관 기관의 공고문과 지침으로 확인
    + 수록 정보와 현행 기준이 다르면 현행 기준을 적용
- (책임 범위) 산출물의 제출과 사용에 따른 결과는 사용자가 책임
    + 책임 대상은 입찰, 평가, 계약의 결과와 그에 따른 법적 책임
    + 스킬 제작자는 산출물의 정확성과 입찰 결과를 보증하지 않음

## 용어

| 용어 | 정의 |
|---|---|
| 슬라이드 | 발표자료의 쪽 1개. 분량은 슬라이드 N장으로 셈 |
| 장, 절 | 목차 단위. 장은 storyboard 의 `chapter`, 절은 `section` |
| 밴드 | 슬라이드 상단 영역. 절 번호, 절 제목, 장 추적기, 헤드라인이 놓임 |
| 헤드라인 | 밴드 가운데의 결론 문장 1개 |
| 마커 | 본문 첫 줄의 소제목. 정사각형 도형과 함께 조판 |
| 수행 Point 밴드 | 본문 아래에 라벨 칸과 한 문장을 담은 띠. 헤드라인과 본문에 없는 판단 기준, 산식, 후속 연계, 선정 사유, 적용 시점, 원칙을 표시 |
| 템플릿 | storyboard 의 `template` 값이 가리키는 조판 방식 |
| 파라메트릭 템플릿 | 항목 수에 따라 배치가 바뀌는 고정 구조 템플릿 (`references/templates.md`) |
| 레시피 | composite 템플릿의 격자와 블록 조합 견본 (`references/recipes.md`) |
| 구성 | 슬라이드 1장의 템플릿 이름. composite 는 레시피 이름으로 구분 (레시피가 없으면 격자 칸 수와 블록 종류 조합으로 구분) |
| 견본 | 문구와 수치를 교체하여 쓰는 예시 슬라이드 묶음 (`assets/*.json`) |
| 커스텀 슬라이드 | 사용자가 제공한 PPTX 의 개별 슬라이드에서 도형 배치를 추출하여 `own:N` 템플릿으로 재사용하는 슬라이드. 서체와 밴드는 스킬 양식을 따름 (`references/custom-slides.md`) |
| 논지 파트 | 과업마다 새로 쓰는 슬라이드 (배경, 전략, 수행계획, 산출물) |
| 공통 파트 | 과업이 바뀌어도 내용이 같은 제안사 소개와 사업관리 슬라이드 |
| 자리 표기 | 확인하지 못한 값을 대괄호로 표시한 문구. 예: `[회사 확인]`, `[확인 필요]`, `[N]명` |
| 섹션대장 | 슬라이드별 RFP 과업, Task, 평가항목 대응을 기록한 `ledger.json` |
| 본문 슬라이드 | 표지, 목차, 간지, 종료를 제외한 슬라이드. 구성 다양성과 배점 귀속 비중 계산의 분모 |
| 채움 비율 | 테두리 상자 안쪽 높이에서 글자가 차지하는 높이의 비율 |
| 본문 세로 채움 | 본문 영역 높이에서 내용 묶음이 차지하는 높이의 비율 |
| 표 글자 채움 | 열별 셀 문구의 한 줄 폭 합이 표 폭에서 차지하는 비율 |
| 상자 글 채움 | 항목 2개 이상을 담는 상자에서 항목 글줄의 한 줄 폭이 상자 안쪽 폭에서 차지하는 비율 (평균과 가장 긴 글줄로 판정) |
| 종합 상자 | 결론 띠 1문장과 대응 항목을 테두리 하나에 담은 composite `summary` 블록. 분석 칸 오른쪽에서 분석 결과를 종합하는 상자로 사용 |
| 워딩 트랙 | 제도 용어의 적용 범위. `meta.track` 의 rnd, mgmt, general |

## 적용 범위

- 주 용도는 공공 용역의 제안 발표자료와 보고회 발표자료
- 민간 기획서, 사내 보고, 교육 자료, 일반 PPT 도 같은 절차와 템플릿으로 산출
- 템플릿과 레시피는 기획 슬라이드의 공통 골격이므로 발주기관 종류와 관계없이 적용
- 제안 외 용도도 용도 적합성 질문 없이 착수 질의로 진행
- 모듈 골격은 `references/methods.md` 의 과업 유형 판별로 정함
    + (사업기획 골격) 신규 사업, 서비스, 제품 기획
    + (전략기획 골격) 중장기 계획, 조직 전략, 로드맵
    + (성과분석과 평가 골격) 성과 진단, 지표 설계
    + (문제해결 골격) 현행 문제의 원인 규명과 개선안 도출. 실태조사, 동향조사, 수요조사 중심 과업 포함
    + (정보화 골격) 시스템 구축 기획, IT 기획
    + (지원사업 운영 골격) 기업지원, 사업화, 창업 분야의 운영기관 공모
    + (연구개발계획 발표 골격) 국가연구개발 신규과제 공모, 연구개발계획서 발표
    + (비R&D 공모 발표 골격) 실증, 컨설팅, 바우처, 수요기반 지원사업 공모
- 기술개발사업 기획연구, 사전기획, 상세기획은 사업기획 골격에 연구개발계획서 목차를 결합
- 기업 R&D 과제와 상용화 지원사업 신청은 사업기획 골격의 신청형 변형을 사용
- 서비스 기획과 IT 기획은 골격을 대상에 맞게 변형 (시장과 사용자 조사, 기능 정의, 아키텍처, 출시 계획)
- RFP 해부, 배점 귀속, 섹션대장은 공공 제안에만 적용
- 워딩 트랙 선택은 공공 제안과 보고회 발표자료에 적용 (그 외 산출 대상은 general)

## 산출 대상

| 대상 | 입력 | 분량 | 경로 |
|---|---|---|---|
| 제안 발표자료 (변환) | 정성제안서(HWPX, DOCX, PDF, MD)와 RFP | 20분 발표 30-45장, 30분 발표 45-60장. 발주기관 지정값 우선 | 원고의 결론 문장에서 헤드라인을 추출. 원고 계위(`가-2`, `[1-2]`)는 Task ID(`M1-T2`)로 치환. 치환 대응표는 섹션대장에 보존 |
| 제안 발표자료 (신규) | RFP | 변환과 동일 | RFP 해부, 제안전략, 스토리라인 순서로 설계 |
| 보고회 발표자료 | 보고서 원고나 주제, 이전 단계 storyboard | 착수 40-55장, 중간 30-40장, 최종 50-60장 | `md2storyboard.py` 초안을 다듬음 |
| 보고서형 PPT | 보고서 Markdown, HWPX 변환본 | 상한 없음. 절 1개당 슬라이드 1장 | `md2storyboard.py --kind report` |
| 브리핑 덱 | 보고서 원고, 조사 결과, 회의 자료 | 5-12장. 장 1개당 슬라이드 1장 | `md2storyboard.py --kind brief [--max N]` |
| 일반 기획 PPT | 주제, 원고, 자료 | 요청 분량 | 과업 유형에 맞는 methods 골격을 적용. RFP 절차는 생략 |

## 절차

```
0 착수 질의 (사용자 확인 1)   이용 안내 제시 후 착수 질의 항목 전체를 한 번에 질의. 사용자가 "바로 실행" 을 명시한 경우에만 기본값 적용
1 입력 변환                   python3 scripts/parse_input.py <RFP 또는 원고> <작업 폴더/출력.md> [--pdf] → md (hwpx 는 --pdf 로 배치 확인용 PDF 추가 생성)
                              python3 scripts/extract_images.py <원본> <img_dir> → 삽입 후보 이미지와 manifest.json (pdf, hwpx, pptx, docx)
2 RFP 해부와 제안전략          00_rfp.md, 00_strategy.md (양식은 references/strategy.md). 변환 경로는 원고에서 역추출. 제안이 아니면 생략
3 구성 확정 (사용자 확인 2)    00_storyline.md(1줄 스토리라인, 장별 메시지, 슬라이드별 헤드라인)를 제시. 공공 제안은 ledger.json(섹션대장)과 배점 귀속 표를 함께 제시 → 승인 후 4단계 착수
4 storyboard 작성              논지 파트를 먼저 작성. 공통 파트(company2slides.py 로 만든 common-slides.json)는 마지막에 복사하여 목차 위치에 배치
5 lint                         python3 scripts/lint.py storyboard.json [--ledger ledger.json] [--layout A4] → 종료 코드 0 이 빌드 조건
6 빌드                         node scripts/build.js storyboard.json out.pptx [--layout A4] → python3 scripts/finalize.py out.pptx → python3 scripts/validate.py out.pptx
7 구조 검수                    python3 scripts/check_layout.py out.pptx → 심층 검토(references/review.md) → 수정 → 재빌드
8 시각 검수와 납품             bash scripts/render.sh out.pptx png_dir 60 → PNG 전량 열람 → 조치 → bash scripts/topdf.sh out.pptx (PDF 동봉 시)
```

- 의존성은 다른 단계보다 먼저 `python3 scripts/setup_deps.py --check` 로 확인
- 미충족 의존성은 `python3 scripts/setup_deps.py` 로 설치
- 단계별 산출물은 파일로 누적
- 응답에는 파일 경로, 진행 상태, 확인 필요 항목만 기재
- 검토 요청 파일과 납품 파일은 실행 환경의 파일 전달 도구로 전달
    + (전달 이유) 작업 폴더가 사용자에게 보이지 않는 실행 환경에서는 경로 안내만으로 파일을 열 수 없음
    + (전달 시점) 3단계 구성 확정의 제시와 재제시(00_strategy.md, 00_storyline.md), 8단계 납품(PPTX, 동봉 시 PDF), 사용자의 파일 요청
    + 재제시에는 바뀐 파일만 전달
    + 지정 폴더의 파일만 전달하는 도구는 사본을 그 폴더에 둔 뒤 전달 (기준본은 작업 폴더의 원본)
    + 전달 도구가 없는 실행 환경에서는 파일 경로를 안내
- 납품 파일(PPTX, 동봉 시 PDF)은 PNG 전량 열람 후 전달
- 완료 보고에는 파일 경로, 열람한 시트 파일명, 미해결 사항, 남은 사용자 확인 항목을 기재
- PDF 를 동봉하면 착수 질의 15번의 근사 렌더링 안내를 완료 보고에 1줄로 다시 기재
- 진행 지점은 세션 인계를 위해 `state.json` 에 기록

## 착수 질의 항목

1. (산출 대상) 제안 발표자료 변환, 제안 발표자료 신규, 보고회 발표자료(착수, 중간, 최종), 보고서형 PPT, 브리핑 덱, 일반 기획 PPT
2. (수행 구조) 산출 대상이 기본 구조를 정하므로 수행 구조 선택 절의 목록에 없는 문서만 확인
3. (대상 지칭어) 본 과업, 본 연구, 본 과제, 본 사업, 본 프로젝트, 본 보고서 중 선택. RFP 표기가 있으면 RFP 표기를 사용
4. (판형) 16:9(기본), A4 가로(인쇄 제출), 10.83×7.5, 4:3
5. (헤드라인 문체) 명사형(기본) 또는 존댓말. 본문은 문체 선택과 관계없이 명사형
6. (색 테마) navy(네이비 블루, 기본), mono(블랙 그레이), 사용자 지정 색 중 선택. 사용자 지정 색은 색상 코드(예: #1B4332)나 색 이름(예: 진녹색)으로 받음
7. (과업 유형과 워딩 트랙) 공공 제안과 보고회 발표자료에만 해당
    + 과업 유형은 전략기획, 사업기획, 성과분석과 평가, 문제해결, 정보화(법정 ISP 대상 여부 확인), 지원사업 운영, 연구개발계획 발표, 비R&D 공모 발표, 혼합
    + 워딩 트랙은 rnd(국가연구개발 성과평가, 사업기획점검, R&D 사업기획), mgmt(공공기관 경영평가), general(기관 자체 평가, 비R&D 예비타당성조사, 일반 용역)
8. (발표 시간과 분량) 발주기관 분량 상한이 있으면 `meta.pageLimit` 에 기록
9. (목차 지정) RFP 지정 목차나 평가항목 순서가 있으면 그 순서를 사용. 일반 용도는 주제에 맞는 목차를 제안
10. (회사 프로필과 로고) 작업 폴더 company.md(양식 `assets/company.md`)의 작성 여부와 로고 파일 경로. 로고가 없으면 회사명 텍스트로 대체
11. (회사 사실 정보) 유사 실적, 조직과 팀 전문성, 투입인력 이력, 재무, 인증의 제공 여부. 미제공 항목은 `[회사 확인]` 자리 표기로 산출
12. (컨소시엄) 참여 여부와 기관별 지분, 투입 인월(M/M)
13. (발주기관 관행) Task ID 표기(`Module 1 - Task 2` 또는 `M1-T2`), 평가항목 병기형 헤더, 경로형 헤더("주제 〉 세부")
14. (문서 언어와 라벨) 한국어 라벨(기본) 또는 다른 언어. 다른 언어면 템플릿 라벨과 언어 태그를 `meta.labels` 에 지정 (영문 발표자료 절)
15. (PDF 동봉) PPTX 와 함께 열람용 PDF 를 전달할지 확인. 기본은 동봉
    + PDF 는 LibreOffice 가 그린 근사 렌더링이므로 PowerPoint 표시와 줄바꿈, 글자 위치가 다를 수 있음을 함께 안내

## 회사 사실 정보

- (범위) 제안사 개요, 조직과 팀 전문성, 유사 실적, 투입인력 이력, 재무, 인증
- 회사 사실 정보는 사용자가 제공한 자료에서만 인용
- 착수 질의 11번으로 제공 여부를 확인
- 미제공 항목은 자리 표기 `[회사 확인]` 으로 남김
- 자리 표기의 용도는 자료 미제공 상황의 표시
- `assets/company.md` 를 작업 폴더에 복사하여 작성 (스킬 폴더의 양식과 견본은 그대로 유지)
- 공통 파트는 `python3 scripts/company2slides.py <작업 폴더>/company.md <작업 폴더>/common-slides.json` 로 생성
- 제안업체 현황 슬라이드의 헤드라인은 company.md 표 값으로 작성
- 헤드라인을 직접 정하려면 company.md 헤드라인 절에 문구를 기재
- company2slides.py 는 남은 자리 표기 건수를 출력
- company.md 는 남은 자리 표기가 0건이 될 때까지 보완
- 사실 정보 슬라이드에는 `factSource` 에 자료명이나 확인 일자를 기재
    + (템플릿) features, staff_card
    + (레시피) company_profile, finance_status, record_cards, infra_tiles, pm_profile, case_card
    + (커스텀 슬라이드) 역할이 company_fact, people_table, pm_profile 인 슬라이드
- `factSource` 가 없으면 lint WARN
- 자리 표기가 남으면 lint WARN
- 완료 보고 직전에 `meta.final` 을 true 로 두면 남은 자리 표기가 lint FAIL 로 바뀜
- 완료 보고에는 미확인 항목 목록과 확인 요청 사항을 기재

## 제도 적용 수준

- (제도 기반) 국가연구개발 과업(워딩 트랙 rnd 의 성과평가 대응, 사업기획점검 대응, R&D 사업기획)은 제도가 절차와 산출물을 정함
    + `references/methods.md` 의 골격과 `references/wording.md` 의 제도 워딩을 기본값으로 적용
    + 골격은 RFP 가 지정한 항목만 가감
- (조건부 제도) 정보화 과업은 법정 ISP 대상 여부에 따라 제도 적용이 달라짐
    + 일정 금액 이상 정보시스템 구축의 사전 ISP 는 법정 의무
    + 법정 대상은 ISP·ISMP 수립 공통가이드의 절차와 산출물 명칭을 그대로 사용
    + 법정 대상에서 제도가 정하는 부분은 4단계 골격(환경분석, 현황분석, 목표모델 설계, 통합 이행계획), 요건 분류 체계, 대가 산정 기준, 국가망보안체계 보안 설계
    + 법정 대상에서도 모듈 명칭과 분할, Task 구성, 조사 설계, 이행과제 우선순위 기준은 발주기관 재량
    + 법정 대상 밖 IT 기획(발주기관이 자체 필요로 발주한 과업)은 RFP 가 정한 범위로 구성
    + 법정 대상 여부는 RFP 의 근거 법령, 사업비 규모, 산출물 목록으로 판별
    + 판별이 불명확하면 착수 질의에서 확인
- (재량) 경영전략, 조직진단, 신사업 발굴, 시설 타당성, 비R&D 지원사업 성과분석, 문제해결 과업은 발주기관과 과업마다 구조가 다름
    + methods 골격은 참고 예시로 사용
    + 모듈과 Task 는 RFP 과업 세부내용과 `00_strategy.md` 의 핵심이슈에서 도출
    + 도출한 모듈과 Task 는 3단계 구성 확정에서 사용자 승인을 받음
    + 예시 골격의 모듈명 복제와 워딩 트랙 밖 제도 용어(전략계획서, 자체평가, 효과성 분석 등)는 결함 (lint WARN)
- 국가연구개발 예비타당성조사는 폐지된 제도
- 후속 제도는 사업기획점검(연구형 사업), 사업추진심사와 설계적합성심사(구축형 사업)
- 비R&D 예비타당성조사는 현행 제도
- 두 제도의 명칭과 절차는 혼용을 막기 위해 착수 시 현행 여부를 확인

## 입력 변환

- 모든 입력 형식은 `scripts/parse_input.py` 로 Markdown 으로 변환
    + (pdf) markitdown 본문에 pdfplumber 표를 덧붙임. 실패하면 pdftotext 로 대체
    + (docx, pptx) markitdown 이 실패하면 python-docx, python-pptx 로 대체
    + (hwpx) python-hwpx 의 export_markdown, HwpxDocument.text.markdown, 본문 XML 직접 추출 순서로 시도
    + (hwp) pyhwp 의 hwp5txt 로 변환. 실패하면 hwpx 저장 후 재시도를 안내
- hwpx 변환의 앞 2개 경로는 표 구조를 회수
- hwpx 본문 XML 직접 추출은 표 셀을 포함한 문단 텍스트만 회수
- 한글이 회수되지 않는 문서는 스캔본이나 서브셋 글꼴 문서로 판단
- 스캔본과 서브셋 글꼴 문서는 사용자에게 OCR 필요를 안내
- 표와 그림 배치를 눈으로 확인할 때는 `--pdf` 로 PDF 를 함께 생성. 쪽이 비어 있으면 `LANG=C.UTF-8 soffice --headless --convert-to pdf --outdir <작업 폴더> <hwpx>` 로 LibreOffice 변환
- 변환 결과가 깨지면 다른 변환 수단을 찾아 원문과 대조
    + (깨짐 신호) 한글 일부 깨짐, 병합 셀 표의 열 손실, 표 구조 손실, 문단 순서 뒤섞임
    + (대체 수단) 다른 텍스트 추출 도구, 원문 쪽을 이미지로 렌더하여 눈으로 판독
    + 사용한 변환 수단과 대조 범위는 완료 보고에 기재
- hwpx 의 PDF 변환기 확보 순서는 rhwp 릴리스 바이너리, rhwp 소스 빌드, LibreOffice H2Orestart 확장
- 앞 순위의 확보를 실제로 시도하여 실패한 경우에만 다음 순위로 이동 (실행 환경의 권한 거부는 아래 rhwp 권한 거부 항목)
- (확보 직후 변환 시험) 각 순위에서 변환기를 확보한 직후 python-hwpx 로 `안녕하세요!` 한 줄짜리 hwpx 를 작업 폴더 밖의 임시 폴더에 만들어 변환을 시험
    + 생성은 `python3 -c "from hwpx import HwpxDocument; d = HwpxDocument.new(); h = d.parts.headers[0]; [f.set('face', '나눔고딕') for f in h.element.iter('{http://www.hancom.co.kr/hwpml/2011/head}font')]; h.mark_dirty(); d.add_paragraph('안녕하세요!'); d.save_to_path('변환시험.hwpx')"` (헤더의 글꼴 이름은 나눔고딕으로 지정. 나눔고딕은 설치 의존성 fonts-nanum 에 포함)
    + 변환은 `parse_input.py 변환시험.hwpx <임시 폴더>/출력.md --pdf` 로 실행하고 PDF 의 Producer 값으로 그 순위의 변환기가 쓰였는지 확인 (rhwp 가 실패하면 parse_input.py 가 LibreOffice 로 넘어가기 때문)
    + PDF 쪽을 pdftoppm 으로 이미지로 바꿔 `안녕하세요!` 가 보이는지 확인. rhwp 는 문서 글꼴이 없으면 빈 쪽 PDF 를 만들므로 PDF 생성만으로는 판정하지 않음
    + 시험이 실패하면 확보가 끝났어도 그 순위를 실패로 보고 다음 순위로 이동
- (GitHub 저장소 연결) 세션에 GitHub 저장소를 연결하는 도구가 실행 환경에 있으면 1, 2순위의 첫 GitHub 접근 전에 호출
    + 인자는 소유자 `edwardkim`, 저장소 이름 `rhwp` 를 각각 따로 전달
    + 도구 응답이 안내하는 접근 경로는 아래 절차에 반영
    + 도구가 없거나 호출이 거부되면 이 단계를 건너뜀
- (1순위 rhwp 릴리스) 저장소 https://github.com/edwardkim/rhwp 의 릴리스에서 현 플랫폼(OS, CPU) 자산을 받아 PATH 에 배치
    + GitHub 주소는 웹 화면 경로와 파일 전달 경로로 나뉨
    + 웹 화면 경로(`releases/latest`, `releases/expanded_assets`, `api.github.com`)가 403 이어도 파일 전달 경로(`releases/download/<태그>/<파일명>`)와 git 프로토콜이 통과하는 실행 환경이 있음
    + 1순위 실패는 파일 전달 경로의 수신 실패로 판정
    + 태그는 `git ls-remote --tags --refs https://github.com/edwardkim/rhwp` 출력의 최고 버전 태그로 확인
    + git 접근이 막힌 경우에만 releases/latest 리다이렉트 최종 주소의 끝에서 태그를 확인
    + 자산 목록은 `https://github.com/edwardkim/rhwp/releases/download/<태그>/SHA256SUMS.txt` 를 `curl -fL` 로 받아 파일명 열에서 확인
    + SHA256SUMS.txt 가 없으면 `releases/expanded_assets/<태그>`, GitHub API `/repos/edwardkim/rhwp/releases/tags/<태그>` 순으로 확인
    + 최고 버전 태그에 릴리스가 없으면(SHA256SUMS.txt 404) 다음 버전 태그로 재시도
    + 선택한 자산은 `https://github.com/edwardkim/rhwp/releases/download/<태그>/<파일명>` 에서 `curl -fL` 로 수신
    + 받은 파일은 `sha256sum -c` 로 대조
    + 대조 결과가 불일치하면 확보를 중단
    + 해제한 실행 파일에 실행 권한을 부여
    + 설치 결과는 `rhwp --version` 으로 확인
- (2순위 rhwp 소스 빌드) 릴리스 자산 수신이 막혀도 git 프로토콜은 통과하는 실행 환경에서 확보 가능
    + `git clone` 으로 받은 저장소를 직접 탐색하여 빌드 방법을 판단
    + 빌드 절차는 착수 시점 저장소의 빌드 설정, 워크스페이스 구성, 툴체인 지정, CI 설정, 개발 문서로 확인 (rhwp 는 변경이 잦음)
    + PDF 내보내기 기능이 있는 CLI 바이너리 타깃만 빌드
    + 검수용 바이너리이므로 빌드 시간이 짧은 프로파일이나 피처 조합을 선택
    + 산출 바이너리는 PATH 상의 `rhwp` 로 배치
    + 동작은 `parse_input.py <hwpx> --pdf` 로 확인
    + 클론 용량이 수 GB 에 이를 수 있으므로 착수 전 여유 디스크를 확인 (빌드 후 클론 폴더는 삭제 가능)
    + git 접근이 막히거나 빌드가 실패하면 3순위로 이동
    + 이동 사유는 최종 보고에 기재
- rhwp 확보 후 `rhwp --help` 에서 PDF 출력 명령을 확인 (v0.8.6 기준 명령은 export-pdf)
    + 명령 이름이 다르면 `scripts/parse_input.py` 상단의 RHWP_PDF_COMMAND 를 교체
    + 인자 형식이 다르면 hwpx_to_pdf 의 호출부를 수정
    + 변환 실패 시 parse_input.py 는 경고 출력 후 LibreOffice 로 전환
    + 실제로 사용된 변환기는 PDF 의 Producer 값으로 확인
- (3순위 LibreOffice H2Orestart) 1순위와 2순위가 모두 실패했거나 rhwp 권한 거부 항목이 3순위를 가리키는 경우에 사용
- (rhwp 권한 거부) 실행 환경의 권한 검사가 rhwp 를 받거나 실행하는 명령(태그 조회, 내려받기, 클론, 빌드, 실행)을 거부한 경우의 처리. 거부가 나오면 rhwp 확보를 그 자리에서 멈춤. 이어서 사용자에게 rhwp 내려받기와 실행의 허용 여부를 질의. 답을 받기 전에는 3순위 확보와 2단계 이후 작업을 진행하지 않음
    + (판정) 명령이 실행되지 않고 실행 환경의 거부 응답만 돌아오면 권한 거부. 명령 실행 뒤의 403, 연결 오류, 저장소 접근 거부는 네트워크 실패로 보고 위 순위 이동 규칙을 적용
    + (질의 이유) 권한 거부는 사용자의 허용으로만 풀림. 질의 없이 3순위로 넘어가면 사용자가 허용할 기회가 사라짐
    + (중단 범위) 같은 rhwp 코드를 다른 경로(2순위 소스 빌드, 다른 내려받기 도구)로 받는 시도도 중단. rhwp 와 무관한 입력 변환(Markdown 변환, 이미지 추출)은 계속 진행
    + (질의 내용) 거부된 명령, rhwp 저장소(https://github.com/edwardkim/rhwp), 허용 시 실행할 명령(릴리스 수신, 필요 시 클론과 빌드, rhwp 실행)을 함께 제시. 출처와 명령을 밝힌 질의여야 사용자의 허용 범위가 분명해짐
    + (답에 따른 진행) 허용하면 1순위부터 다시 확보. 허용하지 않거나 답이 없으면 2순위 없이 3순위로 변환 시험 진행
- 모든 순위가 실패하면 사용자에게 알린 뒤 Markdown 만 사용

## 원본 이미지 재사용

- 제출 원본(pdf, hwpx, pptx, docx)이 있으면 `scripts/extract_images.py` 로 삽입 후보를 추출
- 추출 하한은 한 변 64px, 용량 2KB, 면적 8,192px
- 불릿과 배경 조각은 후보에서 제외
- 하한을 낮게 둔 이유는 작게 삽입된 CI 와 기관 로고의 회수
- 로고 후보는 manifest 의 logo 유형부터 열람하여 확인
- 후보가 많으면 `--min-px`, `--min-kb` 로 하한을 올림
- manifest.json 은 이미지별 크기, 비율, 유형(photo, logo, map, diagram)을 기록
- 출처 쪽 번호는 PDF 에서 뽑은 이미지만 기록 (hwpx, docx, pptx 는 파일 안에 쪽 구분이 없음)
- hwpx, docx, pptx 에서 뽑은 이미지는 ZIP 안 경로(member)를 기록
- 쓰임새는 본문 XML 에서 member 파일을 참조하는 위치로 확인
- (채택 대상) 유사 실적 사진, 현장 사진, 지도, 회사와 기관 로고, 템플릿과 레시피로 재현하기 어려운 아키텍처 도식
- (미채택 대상) 방법론 도식, 차트, 모듈과 Task 구조도, 표 캡처 이미지
- 미채택 유형은 템플릿과 레시피로 다시 조판
- 채택 판정은 사람이 수행
- 스크립트는 후보 목록만 제시
- 채택한 이미지는 composite 와 free 의 image 블록 `src` 에 경로로 지정 (커스텀 슬라이드는 `img{k}` 슬롯)
- 이미지 상대 경로는 storyboard 파일이 있는 폴더 기준
- 원본 이미지의 저작권과 사용 권한은 제안사가 확인

## 수행 구조 선택

- 기본 구조는 모듈과 Task (`meta.structure` 값 module)
- 산출 대상별 기본 구조는 질의 없이 적용
    + (plan) 연구개발계획 발표의 계획서 장 구조
    + (sections) 비R&D 공모 발표의 RFP 장 구조, 보고서형 PPT 와 브리핑 덱의 보고서 절 구조
    + (module) 제안 발표자료, 보고회 발표자료, 기획연구, 일반 기획 PPT
- 목록에 없는 문서와 기본 구조가 맞지 않아 보이는 문서만 착수 질의에서 확인
- 모듈과 Task 구조가 맞지 않는 신호
    + 발주기관이 목차를 지정
    + 제도 서식이 항목을 지정
    + 수행 단위가 연차, 부문, 대상별로 나뉨
    + 절 구조가 확정된 원고를 변환
- (확인 문구 예시) "이 문서는 모듈과 Task 구조보다 계획서 장 구조가 맞아 보입니다. 어느 쪽으로 진행할까요"
- 사용자가 답하지 않거나 판단이 서지 않으면 기본 구조로 진행

### 장 구조를 쓰는 유형

- 연구개발계획 발표와 비R&D 공모 발표는 계획서와 RFP 의 장 구조를 그대로 사용
- 연구개발계획 발표의 수행 단위 표기는 `[1차년도]`, `[세부과제 1]`
- 비R&D 공모 발표의 수행 단위 표기는 `[수행부문 1] 부문명`
- 두 유형은 계획서 항목이나 RFP 항목의 전수 대응을 섹션대장으로 관리 (`meta.structure` 가 plan 이나 sections 이면 lint 는 모듈과 Task 검사 대신 항목 전수 대응을 검사)
- 계획서 항목과 RFP 항목은 `meta.rfp.tasks` 에 등재
- 슬라이드는 `rfpTasks` 로 해당 항목에 대응
- (기획연구 예외) R&D 예산으로 발주된 조사와 기획 과제
    + 목차는 연구개발계획서를 따름
    + 내용 설계는 사업기획 골격을 사용
    + `meta.structure` 는 module

## Task 전수 대응

### ID 체계

- RFP 과업 ID(`T1`)는 섹션대장의 내부 추적에만 사용
- Task ID(`M1-T2`)는 제안사가 설계한 식별자
- Task ID 는 절 제목과 마커에 표기
- 섹션대장은 RFP 과업 ID, Task ID, 슬라이드 ID 의 대응을 보관
- 섹션대장의 슬라이드 목록은 storyboard 의 슬라이드 목록과 1대1 대응

### RFP 과업 배치

- RFP 과업 전건을 `meta.rfp.moduleTasks[].rfp` 에 배치 (누락은 lint FAIL)
- 설계 Task 수가 RFP 과업 수의 60% 미만이면 통합 사유를 `00_strategy.md` 에 기록 (lint WARN)

### 모듈 개요 슬라이드

- 모듈마다 1장 배치 (없거나 2장 이상이면 lint FAIL)
- 템플릿은 `module_overview` (열은 Task, 행은 추진과정, 활용자료, 산출물)
- 모듈 개요용 커스텀 슬라이드는 등록 설정의 역할 module_overview 에 번호를 적어 사용 (`references/custom-slides.md`)
- 해당 모듈의 Task 전건을 표기 (누락은 lint FAIL)
- 모듈 개요 슬라이드는 Task 슬라이드 출현 집계에서 제외

### Task 슬라이드

- Task 전건이 1장 이상의 슬라이드 `moduleTasks` 에 출현 (미출현은 lint FAIL)
- lint 는 슬라이드가 없는 Task 를 결번으로 지목 (예: T1, T3, T4 에만 슬라이드가 있으면 T2)
- 모듈 안 Task 번호는 T1 부터 연속으로 부여 (불연속은 lint WARN)
- 슬라이드 항목은 조사 대상, 자료 출처, 조사 규모, 분석 방법, 산출물, 실측 표본 1개
- 절 제목은 `[Module 1] 모듈명` 형식 (대괄호는 절 번호의 마침표와 겹치지 않게 하는 표기)
- 마커는 `Task 2. Task명` 형식
- 목차와 간지의 모듈 항목도 `[Module 1] 모듈명` 형식

### Task 슬라이드 구성

- Task 마다 내용에 맞는 서로 다른 구성을 설계
- Task 슬라이드 구성 검사는 Task 슬라이드가 3장 이상일 때 적용
- 모든 Task 슬라이드가 같은 구성이면 lint FAIL
- 구성 종류 수가 Task 슬라이드 수의 절반(최소 2종) 미만이면 lint WARN
- 모듈 1개의 Task 슬라이드 3장 이상이 모두 같은 구성이면 lint WARN
- 견본의 차트 데이터, 표 값, 항목 문구는 과업 내용으로 교체
- 견본의 항목 수가 과업과 맞지 않으면 항목 수를 조정
- 항목 수 조정 후에도 어색하면 다른 레시피를 선택
- 주제 제약이 없는 범용 구성
    + (chart_text) 차트 1개와 시사점
    + (chart_two) 차트 2개와 차트별 발견 사항
    + (table) 전폭 표
    + (analysis_four) 차트 4개의 4분면 배치
    + (key_numbers) 핵심 수치와 시사점
    + (illustrative) 산출물 예시 표와 Illustrative 태그
- Task 내용별 구성 예시
    + (조사와 통계 분석) chart_text, chart_two, analysis_four, key_numbers, market_sizing, pest_scan
    + (사례와 경과) benchmark_cases, history_timeline
    + (자료 대조와 목록) table, 표 2개를 나란히 둔 composite
    + (면담과 설문) interview_plan, survey_design, interview_findings
    + (분석 종합과 선별) findings_synthesis, task_funnel, option_evaluation, strategy_review
    + (절차와 단계 설계) verify_steps, kpi_development, steps
    + (구조와 체계 진단) value_chain, industry_chain, alignment_pyramid, logic_model, business_model, swot, env_to_strategy
    + (과제와 정의서) task_definition, project_breakdown
- 예시에 없는 내용은 `references/recipes.md` 에서 용도가 맞는 레시피를 선택
- 파라메트릭 `task` 는 Task 설계표(조사 대상, 자료 출처, 조사 규모, 분석 방법, 산출물)와 실측 표본을 한 장에 담는 구성

### 분량

- Task 슬라이드 1장에는 Task 1건이 기본
- `task_multi` 묶음은 발주기관 분량 제한이 있을 때만 사용 (`meta.pageLimit` 미지정 시 lint FAIL)
- 분량 제한이 있으면 1장에 Task 2-4건까지 묶음 (3-4건은 lint WARN, 5건 이상은 lint FAIL)
- `task_multi` 는 Task 를 열, 항목 라벨(활용자료, 방법, 산출물)을 행으로 둔 매트릭스
- 행 정렬을 위해 항목은 "라벨 : 값" 형식(`"활용자료 : 평가 규정"`)으로 작성
- 분량 제한이 있어도 매트릭스, 표, 단계 구성을 섞어 조판
- 모듈당 슬라이드는 2-8장 (범위 밖은 lint WARN)

## 수행조직

### 템플릿

- 수행조직도는 `org` 템플릿
- 투입인력표는 `table` 템플릿
- 투입인력표의 열은 번호, 역할구분, 성명, 소속, 전공, 학위, 참여기간, 참여율, 경력
- 투입인력은 표의 행 단위로 기재
- lint 가 투입인력표로 인식하도록 마커나 절 제목에 "투입인력" 을 포함
- `staff_card` 는 인력 4명 이상의 경력과 실적을 카드로 보일 때 사용
- staff_card 는 사진이 없으면 사진 열을 생략

### 수행조직도 배치

- 계선은 발주기관, 총괄책임자(PM), 품질관리자(PL), 모듈 팀 순서의 수직 배치
- 품질관리자는 내부 인력이므로 총괄책임자와 모듈 팀 사이에 배치
- 자문위원회는 총괄책임자 우측에 수평으로 연결
- 모듈 상자 수는 설계 모듈 수와 일치 (부족하면 lint FAIL)
- 모듈 상자는 6개까지 1행, 7개 이상이면 2행으로 자동 배치 (대형 과업과 컨소시엄 대응)

### 리더 호칭

- 리더 호칭은 RFP 표기를 사용
    + (총괄 리더 호칭 예) 총괄책임자, 연구책임자, 과제책임자, 사업책임자, PM
    + (품질 리더 호칭 예) 품질관리자, 품질책임자, PL, QA 책임자
- RFP 에 리더 호칭이 없거나 리더를 따로 지정하지 않는 과업은 착수 질의에서 확인
    + (확인 문구 예시) "이 과업의 총괄 리더와 품질 리더를 무엇으로 부를까요. 별도 지정이 없으면 총괄책임자와 품질관리자로 표기하겠습니다"
    + 사용자가 답하지 않으면 총괄책임자(PM)와 품질관리자(PL)를 사용
- 한 발표자료 안에서 호칭은 하나로 통일 (혼용은 lint WARN)

### 인력 일치

- 수행조직도와 투입인력표는 함께 배치 (한쪽만 있으면 lint FAIL)
- 두 슬라이드의 인력 집합은 일치 (한쪽에만 있는 인력은 lint FAIL)
- lint 의 인력 인식 형식
    + (인력 칸) 수행조직도의 pm, qa, 팀원 칸, 머리 행에 성명 열이 있는 표의 성명 칸, 라벨이 성명인 행, staff_card 의 name 은 칸 앞의 성명을 직급과 관계없이 인식 (예: "김수연 부사장" 의 김수연)
    + (그 밖의 문구) `[인력A]` 와 "성명 + 컨설팅사와 연구기관 직급" 을 인식 (예: 수석컨설턴트, 수석위원, 책임연구원, 시니어 매니저, Partner)

### 회사 조직도

- 회사 조직도는 `orgchart` 템플릿
- company2slides.py 가 만드는 조직 슬라이드는 팀별 전문성을 담는 bullets 구성
- 조직 구조도가 필요하면 그 슬라이드를 `orgchart` 로 교체
- 수용 범위는 본부 2-8개, 본부별 팀 1-6개
- 본부가 9개 이상이면 앞의 8개 본부만 조판 (빌드 경고)
- 경영지원(대표 좌측)과 자문위원회(대표 우측)는 대표와 같은 행에 배치하여 계선을 수평 1줄로 유지
- 조직도에는 부서 이름과 팀 이름만 표기
- 팀은 축약 없이 전건을 개별 상자로 조판
- 본부 8개와 팀 6개의 최대 구성은 인력 표를 생략한 전폭 배치에서 지원
- 인력 표를 함께 둔 슬라이드에서 본부가 7개 이상이면 조직도 폭을 본문 폭의 76%로 확대
- 확대 후에도 세로 공간이 모자라면 빌드 경고
- 인력 구성은 `people` 표로 제시

## 목차

- 목차는 RFP 와 문서 목적에 따라 설계
- RFP 지정이 없으면 제안개요, 제안업체 현황, 사업수행계획, 사업관리부문의 장 구성에서 출발 (`references/skeletons.md`)
- 골격의 절 후보는 과업에 필요한 절만 선택

## 배점 귀속

- 비정량 세부평가항목 전건은 1개 이상 슬라이드의 `evalItems` 에 귀속 (0건은 lint FAIL)
- 정량 평가항목(신용등급, 실적 건수)은 슬라이드 배정 대상에서 제외
- 평가항목의 배점 비중 대비 슬라이드 비중이 절반 이하이거나 두 배 이상이면 lint WARN
- 슬라이드 본문의 평가 내부 어휘(배점, 채점, 방어 논리, 결정 장소, 귀속)는 lint FAIL

## 헤드라인

- 헤드라인은 storyline 단계에서 확정
- storyboard 작성 단계는 확정한 헤드라인을 그대로 사용
- 주제별 문형이 있는 슬라이드는 `references/headline-patterns.md` 의 문형에 키워드만 치환
- 문형이 없는 주제는 텍스트 규범에 맞춘 결론 문장으로 헤드라인을 작성
- 헤드라인 상한은 1줄 50자, 2줄 100자 (50자 초과는 lint WARN, 100자 초과는 lint FAIL)
    + 글자 수는 한글 환산 글자 수 (문구 폭을 한글 1자 폭으로 나눈 값. 영문 발표자료도 같은 폭 기준)
- 16:9 보다 좁은 판형은 1줄 상한을 헤드라인 폭 비율만큼 줄여 적용 (A4 43자, 10.83×7.5 40자, 4:3 37자, 2줄 상한은 1줄 상한의 2배)
- 헤드라인은 결론 문장으로 작성 (lint 는 "추진배경" 처럼 공백 없는 2-12자 주제 라벨을 WARN)
- 헤드라인은 1줄과 2줄 모두 18pt 로 조판
- 헤드라인은 문구를 줄여 1줄로 맞춤
- check_layout 은 헤드라인 글꼴 크기의 불일치를 보고
- 근거, 단서, 전제는 `note` 나 `footnotes` 에 기재 (note 앞의 ※ 는 빌드가 붙임)
- 강조 어구 1곳은 `accent` 필드에 지정

### 대상 지칭어

- 대상 지칭어는 RFP 표기를 우선 사용
- RFP 표기가 없으면 산출물 성격으로 선택 (`references/headline-patterns.md`)
- 공공 계약 형식이 학술연구용역이어도 내용이 컨설팅이면 본 과업으로 지칭
- 지칭어 후보가 여럿이거나 RFP 표기가 없으면 착수 질의에서 확인
- 사용자가 답하지 않으면 공공 과업은 본 과업, 민간 과업은 본 프로젝트를 사용
- 발표자료 안에서 지칭어는 하나로 통일 (혼용은 lint WARN)
- 템플릿 라벨과 견본 문구의 과업 표현도 선택한 지칭어로 치환 (치환 대상 목록은 `references/headline-patterns.md` 대상 지칭어 절)
- 치환 예외는 RFP 서식 명칭(과업지시서, 과업 세부내용)과 VISION, SCOPE 같은 구조 라벨
- 제안 외 산출물에 과업 라벨이 남으면 lint WARN
- 제안 전용 라벨은 산출 대상에 맞춰 변경
    + 덱 전체에 같은 라벨은 `meta.labels` 에 한 번 지정 (키와 기본값은 `references/templates.md` 라벨 슬롯 절)
    + 수행 Point 밴드의 라벨 문구(기본 "수행 Point")는 `meta.pointLabel` 로 변경
    + 간트의 과업 열 머리와 보고 행 묶음 이름(기본 "과업", "보고회")은 gantt 의 `taskHead`, `reportHead` 로 변경
    + 표지와 종료 슬라이드의 회사명은 `meta.company` 로 지정

## 텍스트 규범

- storyboard 작성 전에 `references/writing-rules.md` 를 읽음
- (문장) 1문장 1메시지, 본문은 명사형 종결
- (단문) 주어와 서술어가 1쌍인 단문
- (기호) em dash 자리는 쉼표나 마침표로 대체
- (어구) lint FAIL 표현과 lint WARN 어휘의 목록은 `references/writing-rules.md` 를 따름
- (고정 워딩) RFP 핵심 워딩은 표준 표기를 유지
- (수치) 미확인 수치는 자리 표기 `[확인 필요]` 로 표시
- (수행 Point) 밴드는 헤드라인과 본문에 없는 판단 기준, 산식, 후속 연계, 선정 사유, 적용 시점, 원칙을 담을 때만 사용
    + 헤드라인 반복이나 본문 요약만 담은 밴드는 삭제
    + 한 줄짜리 산식이나 단서는 `footnotes` 에 기재하여 본문 높이를 확보
- lint 는 문장 규범 위반을 FAIL 과 WARN 으로 보고

## 영문 발표자료

- 영문 발표자료도 같은 템플릿, 빌드, 검수 절차로 조판
- 텍스트 규범, 헤드라인 문체(착수 질의 5번), lint 문장 규범 검사는 한글 문구에만 적용
    + em dash 와 en dash 검사는 영문 문구에도 적용 (lint FAIL)
- 템플릿과 블록의 기본 라벨은 한국어이므로 `meta.labels` 에 영문 라벨을 덱 단위로 지정 (키, 기본값, 영문 예시는 `references/templates.md` 의 라벨 슬롯 절)
    + 해석 순서는 슬라이드 슬롯 값, `meta.labels`, 기본값
    + 슬라이드마다 다른 라벨만 해당 슬롯에 지정
    + 일부 슬라이드만 영문인 덱은 영문 슬라이드가 쓰는 템플릿의 라벨만 지정하거나 그 슬라이드의 슬롯에 지정
    + 지정하지 않은 키는 한국어 기본값으로 조판되므로 영문 덱이 쓰는 템플릿의 라벨은 모두 지정
    + lint 는 `meta.labels` 의 알 수 없는 템플릿, 블록, 슬롯 이름과 형식 오류를 FAIL 로 보고
- 수행 Point 밴드 라벨은 `meta.pointLabel` 또는 `meta.labels.common.pointLabel` 로 지정
- scope 의 구조 라벨(visionTag, scopeTag, outputTag)은 10pt 로 조판되므로 영문 대문자로 지정 (다른 표기는 check_layout 11pt 하한 WARN)
- PPTX 글자의 언어 태그는 `meta.labels.language` 로 지정 (기본 latin en-US, 한글이 든 run 은 east_asia ko-KR. finalize.py 가 적용)
- 자리 표기(`[회사 확인]`, `[확인 필요]`)는 lint 가 미완성 항목을 찾는 표기이므로 영문 발표자료에서도 그대로 사용
- 공통 파트(company2slides.py 산출)는 한국어 문구로 생성되므로 storyboard 에 옮긴 뒤 영문으로 번역
    + 번역 대상은 headline, marker, section, chapter 와 슬롯 문구
    + id, template, 슬롯 키, 자리 표기는 그대로 유지
- 출처와 주석 줄은 "Source:", "Note:" 로 시작해도 "출처:", "자료:" 와 같이 인식
    + 다른 언어의 주석 토큰은 `meta.labels.notation.source` 에 추가 (기본 토큰은 유지)
- 헤드라인과 마커의 글자 수 상한은 한글 환산 글자 수로 검사 (영문은 같은 폭에 약 2배 글자가 들어감)
- 영문 성명과 영문 투입인력표의 인식 기준은 `references/storyboard-schema.md` 를 따름
- 시각 검수에서 한국어 기본 라벨이 남은 슬라이드가 없는지 확인

    + 셀의 세로 정렬은 표 전체를 가운데로 통일
    + 한 열의 셀은 모두 한 항목이거나 모두 여러 항목으로 구성

    + 여러 줄 셀은 행 높이가 남는 만큼 줄 간격을 1.3배까지 넓힘
    + 표 높이는 본문 영역 안에서 끝나도록 행 수와 행 높이를 조정
- (표 병합) 같은 값이 이어지는 행이나 열은 storyboard 작성 단계에서 병합 여부를 판단
    + 판단 기준은 앞뒤 행의 관계
    + 병합 대상은 상위 분류(구분, 단계, 모듈, 담당)가 실제로 이어지는 행
    + 병합 제외 대상은 값이 우연히 같은 행, 각 행이 독립 항목인 표, 행별 대응을 보여야 하는 비교 표
    + 병합 지정은 storyboard 의 `merged` 필드
    + 빌더는 `merged` 지정대로만 병합
- (정렬) 가로 정렬은 열 단위, 세로 정렬은 행 단위로 통일
    + 항목 1개는 줄바꿈으로 여러 줄이 되어도 불릿 없이 가운데 정렬
    + 항목 2개 이상은 불릿 좌측 정렬과 세로 가운데 정렬
    + 같은 열의 셀은 같은 가로 정렬을 사용
    + 같은 행의 셀은 같은 세로 정렬을 사용
    + 나란히 놓인 같은 계층 상자는 가로 정렬과 세로 정렬을 모두 통일
    + 짧은 라벨 상자는 가운데 정렬
    + 한 상자만 다른 정렬을 쓰는 경우는 강조 목적이 분명할 때로 제한
- (세로 채움) 패널의 남는 높이는 항목 간격(18pt 상한)에 분배
    + 간격 분배의 기준은 PowerPoint 줄 높이(글꼴 크기의 1.4배)로 잰 남는 높이
    + 채움 과정에서 글꼴은 계층 기준값을 유지
    + 목표 채움 비율은 70% 이상
    + 항목 간격을 18pt 까지 넓혀도 항목 2개 이상 불릿 상자의 빈 공간이 45% 를 넘으면 빌드 경고 (빈 공간)
    + 테두리 상자와 패널 안 글 상자의 채움 비율 45% 미만은 check_layout 경고 (상자 내용 부족)
    + 본문 세로 채움 70% 미만은 check_layout 경고
    + 코드 경고는 하한선
    + 눈으로 보아 상자의 절반 이상이 비면 경고가 없어도 조치
- (가로 채움) 글 폭 판정은 실측 글꼴 폭을 여유 계수 0.9 로 나눈 추정 폭을 사용 (실제 렌더링 폭보다 약 11% 넓게 잡힘)
    + 불릿 상자는 상자 글 채움 평균 65% 미만이거나 가장 긴 글줄 80% 미만이면 빌드 경고 (상자 글 채움)
    + 종합 상자는 평균 90% 미만이거나 가장 긴 글줄 95% 미만이면 빌드 경고
    + 종합 상자 항목이 한 줄을 넘기면 빌드 경고
    + 파라메트릭 패널(bullets, cards, conclusion, compare 행 대응)은 가장 긴 글줄에 맞춰 상자 폭을 줄이고 묶음을 가운데에 배치
    + 상자 글 채움 경고는 항목 문구 보강(대상, 기준, 수치 병기)이나 칸 폭 축소로 해소
    + 자리 표기(`[회사 확인]` 등)가 있는 상자와 표는 가로 채움 검사에서 제외
- (높이 배분) 나란한 행(`labeled`, `vsteps`)은 가장 긴 행이 평균 높이 안에 들면 모든 행을 같은 높이로 맞춤
    + 파라메트릭 패널의 높이 상한은 항목 간격을 18pt 까지 넓힌 높이
    + 파라메트릭 패널 묶음은 본문 세로 가운데에 배치
    + 행 라벨 상자와 내용 상자 사이 간격은 0.14인치 (라벨 상자 폭을 줄여 확보)
    + composite 글 상자 블록의 자연 높이는 내용 필요 높이의 1.6배
    + composite 블록이 이웃 칸에 맞춰 늘어나는 상한은 블록별 수용 높이 (`references/recipes.md` 격자 절)
    + composite 의 남는 높이는 도식 행, 블록 수용 높이(표 행 높이, 상자 사이 간격, 도식 크기), 행 사이 간격(0.55인치 상한), 세로 가운데 여백 순으로 배분
    + composite 칸 높이가 내용 필요 높이보다 작으면 빌드가 넘침 위험을 경고
    + composite 의 나란한 칸 가운데 내용이 짧은 칸은 칸 제목 아래 세로 가운데에 배치
    + 표 1개만 담은 composite 칸이 이웃 칸보다 0.3인치 이하로 짧으면 행 높이를 늘려 위아래 끝을 맞춤
    + 본문 묶음은 마커 아래 여백과 쪽번호 위 여백이 같도록 본문 영역 안에 배치
- (채움 조치) 해소 순서는 내용 보강, 상자 축소와 재배치, 표현 형식 교체, 슬라이드 병합이나 재구조화
    + 다음 단계는 앞 단계로 해소되지 않을 때 적용
    + 넘칠 때는 글꼴 크기와 정렬을 유지한 채 글자 수와 항목 수를 줄임
    + 상자를 줄일 때는 남는 공간만큼 묶음 전체를 본문 가운데로 옮김
    + 축소와 재배치 후에도 어색하면 표현 형식을 표, 차트, 셰브론, 도식 중에서 바꿈
    + 빈 공간은 정보가 늘어나는 요소(비중 열, 하베이 볼 열 등)로 보완
    + 보강 항목은 과업 자료에서 확인한 사실로 작성
    + 큰 칸은 채울 내용의 범위를 먼저 결정
    + 내용 상자의 세로 정렬 기본값은 가운데
    + 상단 고정 정렬은 주석과 출처에만 사용
- (기존 슬라이드 수정) 사용자가 특정 슬라이드의 결함을 지적하면 지적한 결함만 고침
    + 도형의 좌표와 크기, 연결 구조, 머리글과 라벨 서식은 유지
    + 배치를 바꿔야 해결되는 결함은 사용자 동의 후 수정
    + 수정 후 원본과 도형 좌표를 대조하여 의도한 변경만 남았는지 확인
- (형태) 파라메트릭, composite, free 템플릿의 기본 도형은 사각형, 반경 0.05인치 이내 둥근 사각형, 셰브론, 직선, 직교 연결선(직선 분해), 원
    + 도식 전용 도형(흐름 화살표, 하베이 볼 부채꼴, strategy 와 house 지붕의 사다리꼴, pyramid 의 삼각형과 사다리꼴, funnel 띠, porter 화살촉, 저장소 원통, flowchart 의 타원과 마름모)은 해당 도식에서만 사용
    + 아이콘, 그라데이션, 그림자, 3D, 알약형 상자, 전폭 색상 띠, 측면 세로 띠, 제목 아래 장식선, 동일 카드 격자 반복은 쓰지 않음
- (차트) 네이티브 차트만 사용
    + 구성비는 원형(6조각 이하)이나 누적 막대
    + 항목 비교는 가로 막대 내림차순
    + 시계열은 세로 막대나 선
    + 데이터 레이블 표시
    + 격자선 미사용
    + 범례는 다계열 차트에만 표시
    + 차트 색은 테마 색의 파스텔 계열
    + 음수 값이 있는 막대 차트는 빌더가 0 기준선과 음수 막대 아래 수치 자리를 조판
- (이미지) composite 와 free 의 image 블록 `src` 에 경로나 data URI 를 지정
    + 로고가 없으면 회사명 텍스트로 대체
    + src 를 적지 않은 image 블록은 점선 자리 상자로 조판
    + check_layout 은 자리 상자의 작은 문구를 경고
    + 자리 상자는 납품 전에 이미지를 지정하거나 다른 블록으로 교체

## 브리핑 덱

- 대상은 회의 보고, 경영진 보고, 조사 결과 공유처럼 보고 자리에서 쓰는 짧은 자료
- 분량 상한은 `--max` 로 지정
- 장 1개는 슬라이드 1장으로 구성
- 장 안의 절은 패널로 배치
- 간지와 목차는 생략
- 표지와 종료 슬라이드는 필요할 때 추가
- 헤드라인은 장 단위 결론 1문장으로 다시 작성
- 상세 근거는 부록 슬라이드로 분리하거나 보고서형 PPT 로 전환
- `md2storyboard.py --kind brief` 산출물은 골격 초안이므로 헤드라인과 템플릿을 다듬어 완성

## 슬라이드 다양성

- 다양성 기준은 모든 산출 대상에 적용
- 다양성 검사의 단위는 구성
    + composite 는 레시피 이름이 같으면 같은 구성
    + 레시피 이름이 없는 composite 는 격자 칸 수와 블록 종류 조합으로 구분
    + 커스텀 슬라이드는 `own:N` 번호별로 구분
- 비중 검사는 본문 슬라이드(digest 슬라이드 제외)가 8장 이상일 때 적용
    + 구성 종류 수는 본문 슬라이드 수의 30%(최소 3종) 이상 (미만이면 lint WARN)
    + 구성 1개의 비중은 본문 슬라이드의 40% 이하 (초과면 lint WARN)
    + 불릿 패널만으로 채운 슬라이드는 본문 슬라이드의 절반 이하 (초과면 lint WARN)
    + 장 1개의 슬라이드 5장 이상이 모두 같은 구성이면 lint WARN
- 같은 구성은 3장까지 연속 배치 가능 (4장 연속부터 lint WARN)
- 구성은 내용 유형에 맞춰 선택
- 표, 차트, 도식, 셰브론으로 표현할 수 있는 내용은 해당 형식으로 조판
- 수치 비교는 표나 차트, 절차와 단계는 셰브론이나 프로세스 도식, 대비는 대비표를 사용

## 구성 선택

- 정해진 구조의 슬라이드(표지, 목차, 간지, 배경과 목적, 목표와 범위, 특징, 추진전략, 프로세스, 모듈 개요, 일정, 수행조직)는 파라메트릭 템플릿을 사용 (`references/templates.md`)
- 분석, 조사 설계, 방법론, 관리 방안은 composite 레시피를 사용 (`references/recipes.md`)
- 레시피 슬라이드는 `assets/recipe-demos.json` 의 같은 recipe 견본에서 slots 를 복사
- 복사한 slots 의 문구와 수치는 과업 내용으로 교체
- 레시피에 없는 단순 구조는 table, chart_text, chart_two, cards, steps 를 사용
- free 템플릿은 템플릿과 레시피로 담기지 않는 슬라이드에만 사용 (발표자료 1건당 3-8장 권장, 8장 초과는 lint WARN)
- 사용자가 자사 PPTX 를 제공하면 `references/custom-slides.md` 절차로 커스텀 슬라이드를 등록
- 내용이 맞는 커스텀 슬라이드가 있으면 `own:N` 을 먼저 사용
- 목록형 상자(경험, 실적, 강점, 역할)는 상자 높이의 70% 이상을 채움 (디자인 시스템의 목표 채움 비율)
- 자료가 모자라면 추가 근거를 찾아 사실을 확보
- 확보한 사실은 역할, 산출물, 성과 수치 관점으로 나누어 기재
- 자료가 없으면 사용자에게 요청하거나 분량이 맞는 구성으로 교체
- 문구가 상자 용량을 넘기면 빌드 경고와 check_layout 결과에 따라 글자 수나 항목 수를 줄임
- 회사 사실 레시피와 features, staff_card 의 자리 표기(`[전문분야]`, `[N]명`, `[대표 실적]`, `[회사 확인]`)는 제안사 자료로 교체
- 빌드는 회사명 자리 토큰(`__COMPANY__`)만 `meta.company` 로 치환
- 전문가 협업체계 레시피(collaboration_structure, advisory_plan)는 워딩 트랙 rnd 의 사업기획점검 대응과 R&D 사업기획 과업에서 사용 (두 과업의 기획위원회 운영 관행)
- 워딩 트랙 mgmt 와 general 은 자문위원회 슬라이드(advisory_plan)만 사용하거나 생략
- 성과분석 레시피(performance_framework, representative_outcome, feedback_plan)는 국가연구개발사업 성과분석 제도의 분석 영역과 소개서 항목을 따르므로 R&D 성과분석 과업에서 사용
    + 분석 영역, 성과유형, 소개서 항목은 해당 연도 성과평가 지침으로 확인
    + 비R&D 지원사업 성과조사분석은 `references/methods.md` 의 투입, 산출, 성과 유형별 지표 구성을 사용
- 공통 파트는 company2slides.py 가 작업 폴더에 만든 `common-slides.json` 의 슬라이드를 복사하여 사용
- 복사한 공통 파트는 id, chapter, secNo 를 목차에 맞추고 내용은 원본을 유지
- 원본 문구나 견본 수치가 과업과 크게 맞지 않으면 과업 내용에 맞게 다시 작성
- 논지 파트 견본은 `assets/proposal-templates.json`(파라메트릭 템플릿별 1장)과 `assets/recipe-demos.json`(레시피별 1장)

## 렌더러 호환

- 납품 기준 렌더러는 PowerPoint
- 검수 이미지(`render.sh`)는 LibreOffice 렌더링 결과
- finalize.py 는 모든 문단에 단어 단위 줄바꿈(eaLnBrk=0)을 적용하여 PowerPoint 의 한글 단어 중간 잘림을 방지
- finalize.py 는 표 셀 위아래 여백을 셀 속성(marT, marB)에 복원하여 PowerPoint 의 기본 여백 적용으로 표가 넘치는 현상을 방지
- finalize.py 는 차트 글자(범주, 범례, 데이터 레이블)에 나눔고딕을 동아시아 글꼴로 지정하여 차트 한글이 테마 기본 글꼴로 바뀌는 현상을 방지
- finalize.py 는 한글이 든 글자 조각의 언어를 ko-KR 로 기록하여 LibreOffice 재저장이 실행 환경 로캘에 따라 한글을 다른 언어(zh-CN 등)로 저장하는 현상을 방지
- finalize.py 는 줄표 불릿("-")이 본문 글꼴을 따르게 하여 PowerPoint 의 불릿 빈 네모 표시를 방지
- LibreOffice 렌더링은 단어 단위 줄바꿈을 무시하므로 검수 이미지에서 잘림이 보이면 문구를 줄임
- 글 상자나 표 셀의 안쪽 폭보다 넓은 어절은 모든 렌더러에서 중간이 잘림 (check_layout WARN)
- 넓은 어절은 띄어 쓰거나 줄여 쓰거나 상자를 넓혀 해소
- PowerPoint 는 LibreOffice 보다 줄 높이를 크게 잡으므로 불릿 상자의 간격 분배는 PowerPoint 줄 높이(글꼴 크기의 1.4배)를 기준으로 계산

## 검수 체계

- 완료 판정의 근거는 렌더링 PNG 열람 기록
- (lint) `scripts/lint.py` 의 검사 항목 (WARN 이 남으면 실패)
    + (구조) 스키마, Task 전수 대응, 섹션대장 일치, 배점 귀속, 분량 상한, 판형 전용 문구(`byLayout`)의 판형 이름과 경로
    + (표기) 문장 규범, RFP 워딩, 대상 지칭어, 절 번호, 주석 ※, 접두 중복, 테마 색 글자 대비
    + (조판) 구성 다양성, 불릿 편중, 표 빈 셀, 치환 문구 분량, 남은 슬롯 표기
- (구조 검수) `scripts/check_layout.py` 의 검사 항목 (WARN 이 남으면 실패)
    + (넘침) 텍스트 넘침 추정, 글 상자와 표 셀의 어절 중간 줄바꿈 추정, 표의 슬라이드 이탈
    + (겹침) 텍스트 상자 사이 겹침(20% 초과 WARN, 30% 초과나 그림이 걸리면 FAIL), 표, 차트, 그림, 채움 상자 사이 겹침(15% 초과 FAIL, 채움 상자끼리는 25% 초과 FAIL), 아이콘과 텍스트 겹침(FAIL)
    + (겹침 판정) 내용 상자 안의 라벨은 줄 단위 글자 영역으로 판정
    + (겹침 제외) 도형 안에 완전히 들어가는 글(깔때기 띠의 단계명처럼 도형 위에 얹은 글)은 아이콘 겹침 판정에서 제외
    + (배치) 본문 여백 쏠림(한쪽 15% 초과이고 반대쪽 15% 미만), 본문 세로 채움 부족(70% 미만), 가장자리 여백, 밴드 이탈, 빈 패널, 상자 내용 부족
    + (표기) 헤드라인 글꼴 일관성, 11pt 미만 본문, 강조색 2곳 이상, 다중 줄 불릿 누락, 표 정렬 혼재
- (시각 검수) `scripts/render.sh` 로 PNG 를 만들어 전량 열람
- 열람은 3-6장 단위 시트(`python3 scripts/sheet.py <png_dir> <out.png> 1,2,3 --cols 3`)로 수행
- 열람한 시트 파일명은 완료 보고에 나열
- (시각 검수 질문) 슬라이드마다 확인하는 질문
    + 헤드라인을 가려도 본문만으로 같은 결론에 도달하는가
    + 3초 안에 먼저 볼 곳이 정해지는가
    + 좌우와 상하의 시각적 무게가 균형을 이루는가
    + 같은 계층 요소의 크기와 간격이 같은가
    + 색과 굵기의 차이가 의미 차이와 대응하는가
    + 같은 구성이 이어져 단조로운 구간이 있는가

### 시각적 확인 항목

- 코드 검사가 놓치는 결함은 슬라이드마다 PNG 로 확인
- 표지와 배경과 목적 슬라이드는 첫인상을 정하므로 가장 먼저 자세히 확인
    + 배경과 목적의 주석이 ※ 로 시작하는가
    + 근거가 항목 본문에 줄바꿈으로 붙어 있지 않은가
    + 리드마다 제목 1문장과 근거 2-3항목이 채워졌는가
    + 표지 제목이 두 가로선 사이 정중앙에 놓였는가

#### 넘침

- 글자가 상자 테두리를 넘거나 상자 밖에서 시작하는가
- 표 셀 안에서 글자가 잘리거나 셀 경계를 넘는가
- 한글 단어가 줄 끝에서 중간에 끊기는가
- 표가 본문 영역 아래로 내려가 잘리거나 슬라이드 밖으로 나갔는가

#### 겹침

- 아이콘, 그림, 도형이 글자를 덮는가
- 상자끼리 겹치거나 연결선이 상자를 관통하는가
- 로드맵과 간트의 막대가 레인 구분선이나 옆 막대에 닿는가
- 연결선과 화살표가 상자에서 떨어져 떠 있는가
- 차트 레이블이 링, 막대, 다른 레이블과 겹치는가

#### 배치

- 헤드라인, 마커, 쪽번호가 밴드 경계나 가장자리 여백을 침범하는가
- 내용이 한쪽으로 몰려 반대쪽이 크게 비어 있는가
- 테두리 상자 안이 절반도 차지 않아 비어 보이는가 (코드 경고가 없어도 판단)

#### 정렬

- 표의 같은 열에서 가로 정렬이 셀마다 다른가 (숫자 열에 우측 정렬과 다른 정렬이 섞임)
- 표의 세로 정렬이 행마다 달라 글자 높이가 들쭉날쭉한가
- 표 분류 열이 병합 없이 비어 표가 끊겨 보이는가
- 나란히 놓인 상자들의 정렬 방식이 서로 다른가 (한쪽은 가운데, 옆은 좌측)
- 1줄 텍스트가 좌측으로 붙어 있거나 여러 줄 텍스트가 가운데로 흩어져 있는가

#### 표기

- 본문보다 작은 글씨의 용도가 분명한가 (근거, 출처, 전제에는 ※ 부착)
- 같은 계층의 글꼴 크기가 서로 다른가
- 한 상자 안 불릿 중 하나만 글꼴이 달라 튀어 보이는가

#### 색상

- 표 헤더나 셀 배경에 팔레트 밖 색(하늘색, 주황 등)이 들어갔는가
- 단위 행이나 빈 행이 투명 처리되어 표 스타일 기본색이 드러나는가

#### 조치

- 발견 항목은 storyboard 를 고쳐 재빌드
- 렌더러 차이로 보이는 결함도 PowerPoint 기준으로 판단

### 규칙 밖 결함 판단

- 규칙에 없어도 보기에 이상한 요소는 결함으로 조치
- 규칙 밖 결함의 예
    + 레이아웃이 깨져 요소가 흩어지거나 한쪽으로 쏠림
    + 도형이나 선이 그리다 만 상태로 남음
    + 한 슬라이드만 글꼴, 색, 간격이 다른 양식으로 표시됨
    + 같은 열이나 같은 계층 상자에서 정렬이 제각각임 (좌측, 가운데, 우측이 섞임)
    + 내용과 관계없는 아이콘이나 마커가 들어옴
    + 빈 상자, 빈 표, 값이 없는 차트가 남음
    + 같은 내용이 두 곳에 중복 표시됨
    + 연결선이 아무 데도 닿지 않거나 방향이 반대임
    + 절 번호가 두 번 나옴 (밴드 번호 뒤 절 제목에 번호를 다시 씀)
    + 번호나 기호가 두 번 나옴 (불릿 도형 뒤 텍스트에 다시 불릿이나 하이픈을 씀)
    + 항목이 여럿인데 불릿이 없어 줄들이 붙어 보임
    + 주석과 출처에 ※ 가 빠짐
    + 절 번호, 마커, 불릿이 있어야 할 자리에 누락됨
    + 같은 계층인데 일부 항목에만 번호가 붙음
- 판단 기준은 실무자가 발표자료로 제출했을 때 지적받을 수준인지 여부
- 조치는 storyboard 수정, 구성 교체, 슬롯 비우기, 슬라이드 분리 중에서 선택
- 원인을 모르는 결함은 해당 슬라이드의 단독 빌드로 재현
- 수정 근거와 남은 결함은 완료 보고에 기재

### 시각 조정 재량

- 검수에서 텍스트가 답답하거나 빈 면적이 크면 슬라이드 안에서 조정
- 조정 수단과 적용 순서는 줄 간격 분배, 상자 크기 조정, 요소 위치 이동
- 글꼴 크기는 같은 계층 전체를 함께 바꿀 때만 조정
- 조정 범위는 같은 계층 요소 전체
- 조정 후 좌우와 상하의 무게, 계층 간 간격을 다시 확인
- 조정 결과가 템플릿의 비례를 무너뜨리면 되돌림
- 조정 후 check_layout 을 재실행하여 넘침과 겹침이 없는지 확인
- 규칙대로 조판한 결과가 보기 나쁘면 보기 좋은 쪽을 선택
- 규칙에서 벗어난 조정은 변경 내용과 이유를 완료 보고에 한 줄로 기재

### 심층 검토

- `references/review.md` 에 따라 배점 10점 이상 세부평가항목에 귀속된 슬라이드를 평가위원 관점으로 1회 검토
- 검토 항목은 수치 무결성, 출처 신뢰도, 논리 비약, 이면 니즈 대응, 변별력, RFP 대응, 발주기관 존중

### 완료 조건

    + 착수 질의 15번에서 미동봉을 고르면 PPTX 만 산출
- lint 와 check_layout 종료 코드 0 (WARN 도 실패로 집계)

- finalize.py 와 validate.py 통과

- 섹션대장의 대응 100% (RFP 과업, Task, 슬라이드)
